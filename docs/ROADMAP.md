# Beacon 第二版路线图

> 本文是第二版路线图真源，定义版本线、阶段目标、退出条件和交付顺序。需求明细见 `docs/PRD.md`，具体架构设计见 `docs/ARCHITECTURE.md` 与后续 ADR / specs。

## 1. 版本策略

Beacon 从项目开始就使用 `MAJOR.MINOR.PATCH` 三段版本号。`1.0.0` 之前属于 `0.y.z` 预稳定阶段；`1.0.0` 之后严格按 SemVer 执行：

- `1.0.1`：修复，不改变功能契约。
- `1.1.0`：新增兼容功能。
- `2.0.0`：破坏性变更。
- 预发布使用 `1.0.0-rc.1`、`1.1.0-beta.1` 这类后缀。

当前仓库已有 `v0.1.0` 到 `v0.19.x` 历史产物，因此第二版不复用 `0.1.x`。第二版从 `0.20.x` 开始：

| 阶段 | 版本线 | 定位 |
|---|---|---|
| Legacy | 0.1.0 - 0.19.x | 第一版探索期，历史冻结，不作为第二版验收基准 |
| P0 | 0.20.x | 规格冻结：全部规格 / ADR、API 契约草案、PRD / 路线图对齐 |
| P1 | 0.21.x | 工程化基建 + v2 控制面基础闭环：monorepo、apps/web 新栈脚手架、UI 博物馆、静态检查最严档三线、Legacy 前端冻结；Agent 身份、注册确认、namespace 隔离、区服权威模型基础可用 |
| P2 | 0.22.x | 全量 mock 管理台：演示模式先行、全站页面 mock 逐页拍板、「交付」大分类 IA |
| P3 | 0.23.x | 集群管理页接真深化：基于 P1 v2 基础 API 补齐 `/servers`、`/zones`、`/namespaces` 的换区工单、zone-tree、draining / default-entry；Q4 冲突可视化与 env 映射延后（FR-177 / FR-178） |
| P4 | 0.24.x | 采样、健康值、调度决策、本机 agent-api + 接真 `/dashboard`、`/service-analysis` |
| P5 | 0.25.x | 每连接明细、跨服消息、payload 审计 + 接真 `/topology` 与可观测页 |
| P6 | 0.26.x | 热冷归档、冷查询、归档清理 + 接真系统设置页 |
| P7 | 0.27.x | 配置中心 V2：权威模型、编辑校验、版本管理接真 |
| P8 | 0.28.x | 文件资产 V2：资产索引、内容预览、安全审计接真 |
| P9 | 0.29.x | 交付编排 V2：变更单、流式数据面、灰度生效编排、整单回滚接真 |
| P10 RC | 0.30.x | RC 稳定、兼容性冻结、GA 准入 |
| GA | 1.0.0 | 正式稳定版，开始严格 SemVer |

`x` 是 patch 号，按需要递增，没有固定上限。阶段没有完成前仍在同一条版本线发补丁，例如 `0.21.0`、`0.21.1`、`0.21.2` 都属于 P1。

## 2. Legacy 冻结策略

- `v0.1.0` 到 `v0.19.x` 作为第一版探索期保留。
- Legacy 旧分期、旧 FR、旧页面原型不再驱动第二版开发。
- 第二版需要的能力必须重新立 FR、写规格、写验收。
- Legacy 前端（`web/`）随 P1 工程化基建整体冻结，第二版管理台另起 `apps/web`；配置中心、文件同步、文件树预览在 P7-P9 按第二版模型重新设计与验收。

## 3. 阶段路线

### P0：0.20.x 规格冻结

目标：把项目从 Legacy 状态拉回可维护的第二版基线。

退出条件：

- PRD 改为第二版基线。
- 路线图定义 `0.20.x` 到 `1.0.0` 的阶段关系。
- 核心边界确认：namespace 强隔离、首次接入人工确认、业务插件只走本机 agent-api、payload 查看必须填原因。
- §5 规格清单**全部完成**（含 API 契约草案入 `docs/API.md`）；规格完成前不进入后续任何阶段编码。

### P1：0.21.x 工程化基建与 v2 控制面基础闭环

目标：把仓库工程底座一次换好，并提前落下 v2 控制面最小可信闭环：agent identity、注册确认、namespace/token/trust、区服权威表与首次分配链路。

交付：

- monorepo 迁移（参考 Vantaloom 布局）：pnpm workspace + Turborepo；`apps/server`（Go 控制面，go:embed / Makefile / CI / 脚本全部打通）、`apps/agent`（Kotlin）、`apps/web`（第二版管理台）、`apps/ui-wiki`（UI 博物馆）；`packages/ui`、`packages/devmock`、`packages/eslint-config`、`packages/typescript-config`。
- `apps/web` 脚手架：Vite + React Router + TanStack Query（服务器状态）+ Zustand（客户端状态）+ react-i18next + MSW；路由 / 布局 / 主题 / i18n 骨架可跑。
- mock 基建：`packages/devmock` 按 API 域组织 MSW handlers，浏览器与测试双端共享，承接 P2 全量 mock 管理台。
- UI 博物馆：`@beacon/ui` 与 ui-wiki 从 Legacy `web/` 内部提升到根级；每个导出控件必须有展示页（覆盖率检查进 CI）；新管理台组件一律取自 `packages/ui`。
- 静态检查最严档三线进 CI 门禁：TS = typescript-eslint strictTypeChecked + stylisticTypeChecked；Go = golangci-lint 全量启用档（禁用项集中声明并注明原因）；Kotlin = detekt 全规则（存量走 baseline，新代码零违例）。
- Legacy 前端冻结（FR-138）：`web/` 不再演进，发布产物只嵌 `apps/web`；真机依赖旧功能时继续运行 v0.19 及更早版本。
- Agent 身份与注册确认（FR-139~FR-141）：agent 首启生成 `identity.yml`，携 `identityId + bootId` 走 `/beacon/v2/agent/register`；pending 经后台确认后转 active，并衔接 legacy 数据面注册；拒绝、允许重新申请、禁用、启用、解绑与 Q3 强制换绑入审计。
- namespace 隔离与区服权威基础（FR-142~FR-143）：v2 权威表纳入 AutoMigrate，namespace token 哈希落库，namespace_trust 授予 / 收回即时刷新快照；approve 创建未分配 server，未分配 server 可首次分配到 zone / BC 集群，已分配直改返回 `rezone_required`。
- 配套 ADR 已随 P0 落地：monorepo 布局与第二版前端栈（ADR-0060）、静态检查最严档三线（ADR-0061，`static-analysis.md` 随 FR-176 实施同步）。

退出条件：`turbo run lint / test / build` 全仓一键绿；三线静态检查门禁生效；ui-wiki 覆盖率门禁生效；新二进制构建产物只嵌 `apps/web`；Go v2 service/handler/router 测试与 agent v2 identity/client 测试通过。

### P2：0.22.x 全量 mock 管理台

目标：把整个管理台按 `docs/UX.md` 与规格用演示模式先做出来、逐页评审拍板，在写任何后端之前消掉最大的不确定性（前端操作）。

交付：

- 演示模式提前落地，作为设计评审载体：mock 数据覆盖空态 / 常规 / 超大量 / 异常四形态。
- 「交付」大分类与全站导航骨架按 UX.md §2 落地。
- UX.md §2 全部页面以 mock 数据可点击、可演示，逐页过 mockup 评审门拍板。
- 页面数据形状只依赖 `docs/API.md` 契约草案，不接真后端。

退出条件：所有页面拍板留档；此后页面结构性变更必须重过评审门。

### P3：0.23.x 集群管理页接真深化

目标：把 P1 已可用的 v2 身份 / namespace / 区服权威 API 接入全量管理台，并补齐换区工单与冲突处置的高风险 UI 闭环。

交付：

- `/servers`、`/zones`、`/namespaces` 从 mock 接真：注册确认、身份绑定、区服分配与信任管理使用 P1 v2 API。
- zone-tree、server list、agent-identities list 的 1000+ 规模搜索 / 筛选 / 分页体验完成。
- 换区工单 UI：已分配服必须解绑 + 重确认，不提供后台直接改派通道。
- default-entry、draining 等区服管理细节在页面内可操作并保留审计入口。

> 延后（本期不做）：Q4 并发身份冲突可视化闭环、env 映射体验从 P3 拆出——P2 全量 mock 未建对应 UI，另立专项 FR-177 / FR-178（待排期，须走 mockup 评审门）后单独交付。

### P4：0.24.x 健康采样与调度闭环

目标：让 Beacon 能作为业务插件的健康调度中心。

交付：

- agent 1s 采样，Beacon 5s 批量入库。
- 健康值模型输出分数、等级、不可调度原因。
- 调度决策记录候选、排除原因、最终选择和失败原因。
- 业务插件通过本机 `agent-api` 获取调度候选，禁止直接依赖 Beacon HTTP。
- `/dashboard` 健康与调度概览、`/service-analysis` 基础指标从 mock 接真（玩家流 / 连接流与告警随 P5 补全）。

### P5：0.25.x 连接、消息与链路追踪

目标：让跨服通信和异常链路可以被排查。

交付：

- 每连接明细按时间分片存储与查询。
- 跨服消息元数据追踪。
- 跨服消息 payload 分日期存储。
- payload 查看必须填原因，并写入审计。
- 拓扑可展示请求流、消息流和异常链路。
- `/topology`、`/commands`、`/audits`、`/alert-events` 从 mock 接真并贯通跳转；`/dashboard` 流与告警补全。

### P6：0.26.x 热冷数据生命周期

目标：让大数据量连接、消息、调度、审计数据可长期保留且可控清理。

交付：

- 热库数据达到保留期后归档到同实例独立 database / schema。
- 配置预留独立归档 DSN，后续可迁移到独立归档库。
- 冷查询需要显式包含归档数据。
- 清理页面支持预览、dry-run、归档校验、执行、失败重试和审计。
- 所有清理必须先归档再删除。
- `/settings`、`/system`、`/system/version`、`/api-keys` 等系统设置页从 mock 接真（采样、保留期、归档、健康权重、信任关系可配置）。

### P7：0.27.x 配置中心 V2

目标：把第一版配置能力按第二版区服权威模型重建，避免继续堆在旧工作台上。

交付：

- 基于 namespace / BC / 大区 / 小区 / 子服的配置作用域与继承关系。
- 配置值来源解释、有效配置预览、跨 namespace 隔离。
- 结构化编辑、schema 校验、diff、版本历史与版本回退。
- 配置中心页面从 mock 接真（「交付」大分类骨架已在 P2 落地）。
- 敏感配置不泄露到日志、审计 detail 和前端明文历史。
- 配置下发走 P9 变更单统一编排，本阶段不单独做配置发布链路。

### P8：0.28.x 文件资产 V2

目标：先把文件资产看清楚，再允许做大规模交付。

交付：

- Agent 上报插件目录 / 配置目录清单、哈希、大小、修改时间。
- 后台按服务器、路径、扩展名、哈希差异搜索与分页。
- 文本文件支持安全预览和 diff，二进制只展示元数据。
- 敏感路径默认禁止查看，查看文件内容必须入审计。
- 大目录、大文件、1000+ 子服场景下页面不阻塞。
- 文件资产页面从 mock 接真。

### P9：0.29.x 交付编排 V2（变更单统一发布）

目标：把配置发布与文件同步统一成「变更单」模型——插件文件差异与配置变更绑成一单，共用一套灰度编排引擎，推送、生效、观察、回滚全链路闭环。

交付：

- Agent 命令通道只做控制面编排，大文件通过流式 HTTP 数据面传输。
- 指定运行中子服作为黄金模板源，扫描文件差异并与配置变更组合成变更单；影响预览、审批、撤回。
- 基于哈希做增量传输，目标覆盖前自动本地备份。
- 统一灰度编排引擎（载荷无关）：全量 / 大区 / 小区 / 单服混合筛选与批次规划，适配 1000+ 目标。
- 推进门 = 人工确认 + 自动熔断：每批生效并确认后才放行下一批；失败率或健康恶化超阈值自动暂停；支持暂停、继续、紧急终止。
- 生效编排：批次内触发子服重启 / 插件热重载；重启依赖宿主自启拉起，超时未回归判生效失败并计入熔断。
- 变更单历史、批次明细、单服状态与一键整单回滚（文件备份还原 + 配置版本回退 + 重新生效）。
- 配置、预览、变更单统一权限风险分级与贯通审计。
- 变更单与交付历史页面从 mock 接真。

### P10 RC：0.30.x 稳定与 GA 准入

目标：冻结契约，进入 1.0.0 前验收。

交付：

- P1-P9 核心 FR 全部完成并验收。
- 升级、回滚、归档迁移、旧数据兼容有证据。
- API、agent-api、数据模型、页面入口完成兼容性冻结。
- 输出 1.0.0 发布说明和迁移说明。

## 4. 第二版开发顺序

1. P0 把全部规格与 API 契约草案冻结；规格未完不进入任何域的编码。
2. P1 一次换好工程底座：monorepo、apps/web 新栈脚手架、UI 博物馆、静态检查最严档三线、Legacy 前端冻结——让后续一切代码都长在新底座上。
3. P2 全量 mock 管理台先行：整个前端操作面在写后端前逐页拍板，之后页面结构性变更必须重过评审门。
4. P3 起后端按域跟进，**每个域落地的同一阶段必须把对应页面从 mock 切真并真机验收**，禁止攒到最后统一联调。
5. P3 先做身份与区服权威（一切真实数据的源头），接真集群页。
6. P4 做健康值和调度闭环，接真总览与服务分析。
7. P5 增加连接、消息和链路追踪，接真拓扑与可观测页。
8. P6 做热冷数据生命周期，接真系统设置页，避免 P5 数据量拖垮主库。
9. P7 重建配置中心，把配置权威模型与编辑链路做稳。
10. P8 重建文件资产索引与预览，先看清文件资产再交付。
11. P9 做变更单统一交付编排，承载插件与配置一体发布。
12. P10 做 RC、兼容性冻结和 GA 准入。

## 5. P0 规格清单

P0 结束前必须**全部完成**以下规格或 ADR：

- 第二版 REST 与 agent-api 契约草案（`docs/API.md`；此后契约变更按 ADR 流程决策，并同步已拍板的 mock 页面）。
- Agent 身份文件、绑定、解绑、冲突处理规格（已落 `docs/specs/v2-agent-identity.md`）。
- namespace 强隔离与互通信任关系规格（已落 `docs/specs/v2-namespace-isolation.md`）。
- 区服权威模型与未分配 agent 处理规格（已落 `docs/specs/v2-zone-authority.md`，含全仓建表约定与权威实体表）。
- 采样、批量入库、健康值与调度决策规格（已落 `docs/specs/v2-metrics-health-scheduling.md`）。
- 每连接明细与消息 payload 存储规格（已落 `docs/specs/v2-connection-message-storage.md`）。
- 热库 / 归档库与冷查询规格（已落 `docs/specs/v2-hot-cold-archive.md`）。
- 核心后台信息架构与演示模式规格（已落 `docs/UX.md`，评审门见 `.claude/rules/ux-spec.md`）。
- 配置中心 V2 权威模型、编辑校验与版本管理规格（已落 `docs/specs/v2-config-center.md`）。
- 文件资产 V2 资产索引、内容预览与安全审计规格（已落 `docs/specs/v2-file-assets.md`）。
- 交付编排 V2 变更单模型、控制面 / 数据面分离、灰度生效编排与整单回滚规格（已落 `docs/specs/v2-delivery-orchestration.md`）。

以上全部完成是 P0 的退出条件；完成前不进入 P1 及后续阶段编码。后端各域实现中如需变更契约，按 ADR 流程决策并同步已拍板的 mock 页面，禁止后端随手改契约。

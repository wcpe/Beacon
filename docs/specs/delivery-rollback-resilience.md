# 功能规格：交付回滚韧性（失败重试 · 目标级子集回滚 · 交付版本与回滚记录 · 回滚预检）

> 状态：开发中　·　关联 PRD：FR-262、FR-270、FR-271、FR-255　·　分支：feature/fr-262-rollback-resilience
> 决策：[ADR-0079](../adr/0079-principal-capability-and-dangerous-operation-approval.md)（危险操作统一审批）、[ADR-0071](../adr/0071-config-gray-effectuation-model.md)（配置灰度生效与版本不可变链）、[ADR-0057](../adr/0057-surface-desensitized-errors.md)（错误脱敏）
> 承接：[v2-delivery-orchestration](v2-delivery-orchestration.md) §4.7（备份与整单回滚）、[delivery-mcp-tools](delivery-mcp-tools.md)

## 1. 背景与目标

[v2-delivery-orchestration](v2-delivery-orchestration.md) §4.7.2 已定下回滚契约：整单回滚、目标级结果落 `rollback_status` / `rollback_error`、**失败目标可重试**、备份缺失目标在前端明示。落地后有三处「规格承诺了、实现没兑现」与一处「规格没写、事故现场需要」：

1. **失败目标可重试只在同包测试里成立**：`applyRollback` 对 `rolling_back` 单有重试语义（仅重置失败目标，不重做配置版本回退），但生产入口 `RequestRollback` 直接以 `409 illegal_state` 拒绝 `rolling_back`——运维在真机上撞到失败目标后**没有任何重试入口**，只能靠「结束回滚」把残留失败当成既成事实收单。
2. **推进器对 `rollback_status` 为空的被覆盖目标静默丢弃**：`advanceRollingBack` 按 `rollback_status` 分支，空值不落任何分支——既不补初态也不计入任何计数。一旦某单进入 `rolling_back` 而全部目标 `rollback_status` 为空（历史数据 / 人工改库 / 初始化未覆盖），自动收单条件 `terminal > 0` 永假，单**永久停在 `rolling_back`**，只能人工「结束回滚」。
3. **回滚粒度只有整单**：事故现场往往是「某个小区的那几台配错了」，却只能整单回滚——把没问题的 97 台一起打回，二次事故风险远大于原始故障。
4. **回滚不可见**：每台服「现在跑的是哪一单交付的版本」全站无处可查；一次事故里发生过几次回滚、谁发起的、为什么、打到哪几台、每台成没成，只有审计流里零散的记录，运维要拼。回滚预检（哪些台因备份缺失**不可能**文件回滚）在 §4.7.2 承诺在前端明示，实际到点才在结果里看到 `failed`。

**目标**：把 §4.7.2 的承诺补成真，并把回滚从「整单原子动作」升级为「可按目标子集执行、动作与结果全程可查」的运维能力，同时把「哪些台不可回滚」在动手之前说清楚。

**范围内**：控制面回滚编排与生产入口、目标级回滚 API 与 MCP 面、回滚动作记录与交付版本读模型、管理台目标列表勾选与回滚预检。
**范围外**：agent 侧备份与还原实现（归交付数据面，本组不改）、状态机与幂等语义收口（FR-263）、`pending_approval` 卡死收敛（FR-259）、回滚的自动化编排（观察窗熔断触发回滚）不在本组。

## 2. 需求（要什么）

### 2.1 FR-262r：回滚失败可重试 + `rolling_back` 卡死修复

- 失败目标（`rollback_status=failed`）必须有**生产可用的重试入口**，且重试**只重推失败目标**，不重做配置版本回退（配置回退在不可变版本链上只能发生一次，重做会污染链）。
- 重试必须**走统一审批**（理由见 §3.2），原因必填、入审计、落回滚动作记录。
- `advanceRollingBack` 必须对每个目标的 `rollback_status` **穷尽分类**，不得有目标被静默丢弃：
  - 空值 + 曾被覆盖磁盘（`pushed_at` 非空）→ **就地补回滚初态**（有备份 `pending`、无备份 `failed`），纳入本次推进；
  - 空值 + 从未覆盖磁盘（`pushed_at` 为空）→ 归为「非回滚目标」，显式计数；
  - 单内回滚目标全部为空（无实际回滚工作）→ 自动收单，不再永久停留 `rolling_back`。

### 2.2 FR-270：目标级（子集）回滚

- 管理台可在变更单的**目标列表勾选**若干目标发起回滚（支持按批 / 区筛选后再勾选），原因必填。
- **只回滚选中目标的文件**：未选中目标一个字节都不动。
- **配置版本不回退**，且在界面与记录中**明示「配置未回退」**：子集回滚不生成配置中心新版本、不清 pin。
- **全选等价整单回滚**：选中集合覆盖全部回滚目标时，行为回落为既有整单回滚（含配置版本回退与单主状态迁移）。
- **单主状态不变**：子集回滚不改变更单主状态（已完成的单仍是 `completed`）；结果落在目标级 `rollback_status` / `rollback_error` 与独立回滚动作记录上。
- MCP 同能力：`beacon.delivery.order.rollback` 扩 `serverIds` 入参（省略即整单回滚），不新增工具（理由见 §3.4）。

### 2.3 FR-271：交付版本可见与回滚记录

- 每台服的**「当前交付版本」**= 该服最近一条 `activated` **且未被回滚**的交付目标记录，内容含变更单号 / 单标题 / 生效时间；该服被回滚后，展示按「未被回滚」规则**正确回退**到上一单（没有则显示无）。
- 展示于**服务器详情**与**变更单目标列表**。
- 每次回滚动作（整单 / 子集 / 重试）落**可查记录**：谁 / 何时 / 为何 / 哪些台 / 每台结果，并可标注本次是否回退了配置版本。
- 记录从**变更单**（单详情内回滚记录视图）与**审计**（`/audits` 按 orderId 过滤）两路可追溯。

### 2.4 FR-255r：回滚预检 UI

- 回滚确认前展示「**哪些目标不可文件回滚**」（`backup_present=false`），并给出数量与逐台清单。
- 预检在**申请之前**可见，不等于结果；申请后仍以目标级结果为准。

## 3. 设计（怎么做）

### 3.1 数据模型

新增两张表（[ADR-0071](../adr/0071-config-gray-effectuation-model.md) 的「版本不可变链」不受影响；不含 MySQL 专有类型，遵守架构不变量 §4）：

`change_rollback_record`（回滚动作记录，一次动作一行）：

| 列 | 说明 |
|---|---|
| `id` | 自增主键 |
| `order_id` | 归属变更单（索引） |
| `kind` | `order`（整单 / 重试）/ `targets`（子集） |
| `reason` | 本次动作原因（必填，来自申请 / 审批冻结 payload） |
| `operator` | 发起人（审计引用） |
| `config_rolled_back` | 本次动作是否回退了配置版本；子集恒 `false` |
| `target_count` | 本次动作涉及目标数 |
| `created_at` / `updated_at` | 动作时间 |

`change_rollback_record_target`（动作内逐台）：

| 列 | 说明 |
|---|---|
| `id` | 自增主键 |
| `record_id` | 归属动作（索引） |
| `server_id` | 目标服 |
| `result` | 该台在**本次动作**里的结果快照：`pending` / `running` / `rolled_back` / `failed` |
| `error` | 该台失败原因（脱敏，[ADR-0057](../adr/0057-surface-desensitized-errors.md)） |

> **为何另建表而不是直接读 `change_target`**：`change_target.rollback_status` 是**目标当前回滚态**（会随后续重试 / 子集动作覆写），记录需要的是**每次动作各自的逐台结果**。两表职责分离：动作记录回答「发生过什么」，目标行回答「现在是什么」。逐台结果在**终态迁移时**写入动作记录，动作创建时按当时实际状态初始化，故无需回填。

### 3.2 回滚重试走审批（FR-262r 的关键取舍）

**结论：重试与首次回滚同为 `delivery.rollback` operation，走统一审批，原因必填。**

理由：

1. §4.8.1 风险矩阵把「整单回滚」列在**高**风险一档（权限 + 原因 + 二次确认 + 审计），并明确本域**不新造 `delivery.*` 能力位**、一律登记为统一审批 operation。重试与首滚的**副作用完全同质**（都会实打实覆盖线上文件、都会令目标重启），把重试降级为直执等于开一个绕过审批的旁路，与矩阵直接冲突。
2. FR-211 的分档（「止损 direct、推进 approval」）中，回滚属**破坏性推进**一侧而非止损：暂停 / 终止只是停止后续动作（可逆性由「单还在」保证），回滚是**改写线上运行态**。
3. 重试的输入（原因、期望状态哈希、幂等键）与首滚同形，复用同一 operation 与同一票据契约，前端与 MCP 不需要第二套语义；必须区分「这是重试」的地方只在**执行适配器内部**。

因此实现只放开状态准入：`RequestRollback` 接受 `rolling_back`，冻结 payload 记 `retry: true`；执行适配器在 `rolling_back` 分支只重置失败目标（`ResetFailedRollbackToPending`），**不碰配置版本、不改单主状态**。

### 3.3 目标级回滚编排

- **入口**：`POST /admin/v2/change-orders/{id}/rollback/targets`，体 `{reason, serverIds}`，返回 `202` 票据（`delivery.rollback`）。`serverIds` 必填非空、去重、上限 1000（对齐本域目标量级）；`reason` 必填。
- **准入**：单状态 ∈ {`completed`, `paused`, `cancelled`}（与整单回滚同集，子集回滚同样只对已推送过的单有意义）。
- **落库（申请批准后在审批执行事务内）**：
  1. 校验：每个 `serverId` 必须是本单目标且 `pushed_at` 非空（曾覆盖磁盘）；越界目标整单拒绝（不部分执行）。
  2. **全选判定**：若选中集合 = 本单全部回滚目标，则**回落整单回滚路径**（配置版本回退 + `rolling_back` + 单主状态迁移），与「全选 = 整单回滚」语义一致。
  3. 否则：置选中目标 `rollback_status`（有备份 `pending` / 无备份 `failed` + 原因）与 `rollback_error` 清空，**单主状态不动**，写一条 `kind=targets`、`config_rolled_back=false` 的动作记录 + 逐台行。
- **推进**：编排器在既有推进循环里增加一路**目标级回滚扫描**——取「有目标处于 `rollback_status ∈ {pending, running}` 且单状态 **不是** `rolling_back`」的单，对其中目标复用 `dispatchRollback` / `reconcileRollback` 逐台推进。与整单回滚**互斥**：整单回滚推进的单被排除在目标级扫描之外，杜绝同一目标被两条路径同时下发。
  - 目标级回滚**不改单主状态、不做自动收单**（单可能长期停在 `completed` 而个别目标在回滚），失败目标同样可重试。
  - `restart` 生效方式的目标级回滚复用同一套心跳回归判定（`activating_started_at` 锚点），锚点由本次动作重置。
- **审批适配**：`authz.OperationDeliveryRollback` 的领域执行适配器按 payload 的 `serverIds` 分支——有 `serverIds` 走目标级、无则走整单（原语义不变）。历史申请（无该字段）行为不变。

### 3.4 MCP 面：扩参而非新增工具

**结论：扩 `beacon.delivery.order.rollback` 的 `serverIds` 入参。**

理由：该工具与 HTTP 端点是**同一个 operation**（`delivery.rollback`）、同一个 202 票据契约、同一份原因要求与同一套幂等键语义；新增 `beacon.delivery.rollback.targets` 会让同一个危险动作在目录里出现两个等级 / 两条可见性规则 / 两处拒绝文案，机器主体难以判断该用哪个，且与既有「六类申请动作」的对称性被打破。扩参对既有调用方**逐字兼容**（省略即整单回滚）。等级沿用 `critical` + `AutomationOnly`。

### 3.5 交付版本读模型（FR-271）

- **定义**：`serverId` 的当前交付版本 = `change_target` 中 `status='activated'`、`rollback_status` 非 `rolled_back` 的**最新一条**（按 `activated_at` 倒序）所属变更单（`orderId` / 标题 / `activatedAt`）。
- **回退语义**：某服整单或子集回滚成功后该行 `rollback_status=rolled_back`，被排除出候选，自然回退到上一单；无候选则展示「无交付记录」。**不引入第二真源**——读模型直接建在既有 `change_target` / `change_order` 上，不新增冗余状态列。
- **端点**：`GET /admin/v2/change-orders/delivered-versions?serverIds=a,b,c`（`serverIds` 逗号分隔、上限 100）。返回逐服一条（无记录的服**不回行**，由调用方补「无」）。批量语义避免目标列表 20 行触发 20 次查询。
- **挂载**：变更单目标列表每行展示该服当前交付版本（单号 / 标题 / 时间，可跳单）；服务器详情的交付区块同源取值。

### 3.6 回滚记录可查（FR-271）

- **变更单一路**：`GET /admin/v2/change-orders/{id}/rollback-records` 返回该单全部动作（倒序）与逐台结果，单详情内展示。
- **审计一路**：每次动作仍写既有 `delivery.order.rollback` 审计（整单 / 子集 / 重试同一动作码，detail 增 `kind` / `serverIds` / `recordId` / `retry` / `configRolledBack`），`/audits?orderId=` 即得完整链路（§4.8.2 既有承诺）。
- 两者**同源**：动作记录与审计在同一事务内写入，`recordId` 互指，任一路都能定位另一路。

## 4. UX / 交互

- **用户任务**：事故中值班运维要「精确打回出问题的那几台」并留下可交代的记录；动手前要知道「有没有台根本回不了」。
- **进入路径**：`/changes/history` → 变更单详情（目标列表 Tab / 回滚记录）；`/changes` 详情同源。
- **操作闭环**：
  1. 目标列表新增**勾选列**（支持先按批次筛选再勾），选中若干目标后「回滚选中目标」按钮可用并提示已选台数；
  2. 点开**高摩擦确认弹窗**：明示「仅回滚 N 台的文件，**配置版本不会回退**」，列出台数、备份缺失台数，原因必填；
  3. 提交得到 `202` 票据（申请号 + 去审批中心），状态不立即变化；
  4. 批准后目标级 `rollback_status` 逐台推进，状态墙按既有 5s 轮询反映；
  5. 单详情「回滚记录」区按动作倒序列出：谁 / 何时 / 为何 / 台数 / 是否回退配置 / 逐台结果。
- **全选**：勾满全部回滚目标时按钮文案与提示切换为「整单回滚（含配置版本回退）」，走既有整单入口。
- **预检（FR-255r）**：整单回滚与子集回滚的确认弹窗内先展示预检行——「N 台因备份缺失不可文件回滚」并列出 serverId；预检数据取自目标列表的 `backupPresent`，**拿不到时显示「预检不可用」而不是显示 0 台**（避免把未知伪装成安全）。
- **状态设计**：空态（本单无回滚记录 / 无目标）、加载（既有 `AsyncSection`）、错误（脱敏文案 + 重试）、超大量（目标列表沿用分页与虚拟化，勾选跨页保留）。
- **IA 挂载**：无新页面、无导航变更——`docs/UX.md` §2「变更交付」大域下 `/changes` 与 `/changes/history` 的既有详情页内增强，属**非结构性改动**，不过 mockup 评审门。

## 6. 验收标准

- **FR-262r**
  1. `rolling_back` 单的重试申请在生产入口被接受（`202` 票据），批准后**仅失败目标**被重置重推，配置版本回退只发生过一次（不可变链上无第二个新版本），单仍为 `rolling_back`。
  2. `rollback_status` 为空但 `pushed_at` 非空的单，推进后该目标**被补入回滚并下发命令**（不再静默丢弃）。
  3. `rollback_status` 全为空且无回滚目标的单，自动进入 `rolled_back`（不再永久停留），审计记 `auto:true` 与「非回滚目标」计数。
- **FR-270**
  4. 20 台已完成单选中 3 台发起子集回滚并批准：仅这 3 台被下发回滚命令，其余 17 台的 `rollback_status` 保持空、未收到命令；变更单主状态仍为 `completed`；配置中心无新版本、本单 pin 仍在（**配置未回退**在记录中为 `false` 并在界面明示）。
  5. 选中集合等于全部回滚目标时，走整单回滚语义（配置版本回退 + 单状态迁移到 `rolling_back`）。
  6. 选中非本单目标或未曾推送的目标 → 整单拒绝（`400`），无部分落库。
  7. MCP `beacon.delivery.order.rollback` 传 `serverIds` 与 HTTP 子集端点等价；省略时行为与改动前逐字一致。
- **FR-271**
  8. 某服被单 A 交付后显示 A（单号 / 标题 / 时间）；单 B 再交付该服后显示 B；B 被回滚后**回退显示 A**；A 也被回滚后显示「无交付记录」。
  9. 一次整单回滚 + 一次子集回滚 + 一次重试各落一条动作记录，逐条含操作人 / 时间 / 原因 / 台数 / 配置是否回退 / 逐台结果，且 `/audits?orderId=` 能定位到同一动作（`recordId` 互指）。
- **FR-255r**
  10. 存在 `backupPresent=false` 目标的单，打开回滚确认即见「N 台不可文件回滚」与 serverId 清单；预检数据缺失时显示「预检不可用」。

## 7. 风险 / 待定

- **目标级回滚与整单回滚并发的互斥**：仅靠「整单推进的单被排除在目标级扫描外」保证；若未来整单回滚支持「完成后追加子集」，需重新审视。当前以单状态做互斥，不做目标级锁。
- **子集回滚的配置语义**：本组按已拍板口径「配置版本不回退」实现并在界面 / 记录明示。若某单的故障根因确实在配置，子集回滚**不会**修复它——界面提示必须让这一点无法被忽略（文案写在确认弹窗内，不是折叠的说明）。
- **交付版本读模型的开销**：`delivered-versions` 为每服一次「按 `activated_at` 倒序取一条」的查询，批量以 `server_id IN` 聚合；100 台上限下单次查询可控，未见索引压力时不为它新增索引。
- **动作记录的保留**：不设清理策略（单删除时级联），与变更单同生命周期；记录量级为「单×回滚动作数」，无爆炸风险。

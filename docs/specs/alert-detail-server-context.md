# 功能规格：告警详情关联服务器近期状态与时间线

> 状态：已实现（单测通过；真机验收待做）　·　关联 PRD：FR-230（增强 FR-157 / FR-89）　·　分支：feature/alert-detail-server-context

## 1. 背景与目标

> ⚠️ 已按评审重写。原稿把「告警时间线」写成取**告警环形缓存**、把「近期状态」当作需新造的数据源——**前提过期**。

现状：告警已落库（FR-89 / ADR-0041），`/alert-events` **详情面板已存在**（`apps/web/src/pages/alert-events.tsx`），单条 `alert_event` 有 `type` / `level` / `status` / `handled*` 等。运维真正缺的是：打开一条告警时，**把「该服近期状态」与「该服历史告警」并排呈现**，以便 5 秒内判断"已过去 / 需立刻处理"。

本 FR 是**详情面板的增强**，不是新页面、也不是新存储。

## 2. 需求（要什么）

- 详情面板内嵌**该服务器近期状态**：当前健康级别 / 分数、在线与否、最近采样指标（取健康既有真源）。
- 内嵌**该服告警时间线**：从 **`alert_event` 表**按 `serverId` 查近期条目（时间、类型、级别、状态、处理人），能看出"反复发生"还是"一次性"。
- 数据**不复制存储**：状态实时查健康真源，时间线实时查 `alert_event`。

范围内：详情聚合接口 + 前端内嵌视图。
不做（范围外）：新的历史存储（`alert_event` 已是历史）；跨服对比视图。

## 3. 设计（怎么做）

- **聚合接口**：`GET /admin/v1/alert-events/{id}/context` 返回
  - `server`：`{ serverId, online, level, score, reasons[], sampledAtMs }`（取健康既有真源）
  - `metrics`：最近一次 / 短窗口既有指标子集
  - `timeline`：`alert_event` 表按 `serverId` 的近期条目，**建议最近 20 条 / 近 24h**（用户已给默认）
- **数据源**：`server`/`metrics` 取健康与指标真源；`timeline` 查 `alert_event`（**不再查内存环**）。
- **观测范围**：循 FR-213 契约，`timeline` 不越出当前观测范围。
- **无 `serverId` 的集群级告警**：退化为展示**该 namespace 的近期状态 / 告警**，或仅显示告警本身（用户已给默认）。

## 4. UX / 交互

- 用户任务：打开告警 → 立即判断"要不要现在处理"。
- 进入路径：`/alert-events` 行点击 → **既有详情面板**新增两块区域。
- 操作闭环：点告警 → 面板显示「服务器近期状态卡」+「告警时间线」→ 反复 offline 判需处理；显示已恢复 online 判已过去。
- 状态设计：服务器已归档 / 无数据 → 空态；加载中 → 骨架屏；时间线条数上限有提示。
- IA 挂载：可观测域 `/alert-events` 详情；不新增页面。

## 5. 任务拆分

- [x] 聚合接口 `GET /admin/v1/alert-events/{id}/context`
- [x] `alert_event` 按 `serverId` 的有界查询（窗口：20 条 / 24h）
- [x] 健康 / 指标真源读取复用
- [x] 前端：既有详情面板内嵌状态卡 + 时间线
- [x] 文档同步：PRD 状态、API、CHANGELOG

## 6. 验收标准

- 打开任一含 `serverId` 的告警，详情可见该服近期状态与 ≥1 条时间线（数据来自 `alert_event`）。
- 时间线按时间倒序、含级别与处理状态，条数有上限（20 / 24h）。
- 服务器已归档 / 删除 → 降级空态不报错。
- 无 `serverId` 告警 → 按默认退化，不报错。
- 接口不返回敏感数据（循 FR-209）。

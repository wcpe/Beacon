# ADR-0084：保留 v1 / v2 双 agent 注册端点，只消除语义歧义，不退役任一端点

**状态**：已接受（决策部分）；实现并入 FR-233，待排期

## 背景

Beacon 的 agent 注册存在**两个同名端点**：

| 端点 | 凭据 | 职责 |
|---|---|---|
| `POST /beacon/v1/agent/register` | 共享 token（`agent-token`，`agentTokenMiddleware`） | **数据面注册**（写内存 registry + `instance.register` 审计）；命中共享 token 时同时作为 **FR-222 机器注册**的判定依据，开启 `mcp.allow-machine-register` 后直落 active |
| `POST /beacon/v2/agent/register` | namespace token（`namespaceByToken`，按库中哈希校验） | **身份状态机**（FR-139/140/141）：pending → 人工审批 → active，active 后再衔接 v1 数据面注册 |

2026-09-24 用 JianManager 搭建生产环境（12 实例 + Beacon 集成）时，该双端点结构直接造成两类误判：

1. **外部搭建方的误判**：观察到「v1 与 v2 都能注册」，判定「功能重叠、应退役一个以免误会」——但实测插件（`BeaconApiRegister.kt`）**只走 v2**，于是按「退役 v1」的假设排查，方向完全错。
2. **插件自身的误判**：`hasV2Identity() = identityId.isNotBlank() && bootId.isNotBlank()` 在插件**任何正常启动**时都为真（两者都是首启自动生成），因此 `register()` 恒定走 v2；而环境配置里的 `bootstrap-token` 是 **v1 的共享 token**，用它对 v2 认证必然 **401**。真机日志持续 `POST /beacon/v2/agent/register 状态=401`。

排查中确认的真实关系是：**v1 与 v2 不是并列的二选一，而是串联**——`registerLegacy`（v1）的**唯一外部入口**是 v2 的 active 分支（`BeaconApiRegister.kt:79-80`）与「无 v2 身份」回退分支（`:20-21`），而后者在有身份文件时不可达。

## 决策

### 1. 两个端点都保留，不退役任一端点

- **不退役 v2**：它是 FR-139/FR-140/FR-141 的**唯一身份注册入口**，退役即砍掉身份状态机与人工审批能力。
- **不退役 v1**：它是 FR-222 机器注册通道与**全部数据面端点**（heartbeat / stream / files / override-sets / config / commands）所在的路由组，退役范围远超"注册"。
- **不合并两端点**：v2 需要 namespace token（分权设计，FR-142 强隔离），v1 需要共享 token（内网信任，FR-222）；合并必然让其中一方放弃凭据模型，属安全边界变更。

### 2. 只做「消除歧义」的四项改动（FR-233）

1. **v1 的 `/register` 更名**为 `/data-plane/attach`，语义显式化为「挂载数据面」而非「注册身份」；旧路径保留**一个版本周期的兼容别名**并在响应头回带 `Deprecation`。
2. **v2 `/register` 的 handler 注释与 spec 显式声明**「机器注册直落**不**在本端点，见 v1 + `allow-machine-register`」。
3. **两端点 spec 首段交叉引用**，各自说明与另一者的分工。
4. **配置注释澄清**：`bootstrap-token` 供 bootstrap 阶段**观察 v2 身份状态**（`bootstrapRegister`），**不是**机器注册凭据；机器注册凭据是 v1 的共享 token。

### 3. 明确记录「不退役」的理由（本 ADR 的主要价值）

本 ADR 的产出不是新功能，而是**把一次真实误判固化为不可重提的结论**，避免后续再次提出「退役一个以免误会」。

## 与既有 ADR / FR 的关系

- **不取代**任何 ADR。ADR-0004 / 0014 的 serverId bootstrap 结论、ADR-0076 的 Bootstrap/Active Runtime 分层、ADR-0079 的审批模型均不变。
- **增强** FR-222（机器注册通道）、FR-139/140/141（身份状态机）、FR-142（namespace 强隔离）——仅为它们补充可辨识性，不改其语义与凭据模型。

## 理由

- **同名不同职责是真实成本**：本次误判消耗了外部搭建方的排查时间，且若照「退役 v1」执行，会把机器注册通道与数据面一起砍掉（v1 路由组承载全部数据面端点）。
- **凭据模型是安全边界**：v1 共享 token 支撑 FR-222 的「受信内部调用方」判定（`agent_machine_register.go` 明文要求「分支依据是中间件判定的调用方类型 + 部署开关，**绝不取自请求体**」）；v2 namespace token 支撑 FR-142 的强隔离。二者不可互换。
- **插件行为是设计使然，非缺陷**：`hasV2Identity()` 恒真意味着「现代 agent 一律先过身份状态机」；这是 FR-140「首次接入人工确认」的落地方式，不应为了迁就旧配置而回退。

## 后果

### 正面

- 后续接入方（JianManager / 自建平台 / 手工部署）能一眼分辨「注册」与「挂载数据面」。
- 机器注册的正确启用方式（`allow-machine-register: true` + 强随机 `agent-token`）成为文档化路径，与 FR-222 的真机验收结论对齐。

### 约束与迁移

- 更名需插件与外部平台同步；兼容别名窗口为一版本周期，届时删除须再走一次 RFC。
- `Deprecation` 响应头为新增，旧客户端忽略即可（非破坏性）。

### 反面 / 未做

- **不解决「插件用 bootstrap-token 打 v2 得到 401」这一现象本身**：该现象的正确解法是**启用 FR-222 机器注册**（`allow-machine-register: true` + 强随机 token），或走人工审批（v2 落 pending → 管理台确认）。本 ADR 只保证该因果在文档中可查，不改运行时行为。

## 备选方案

### 方案 A：退役 v2，让 v1 承担全部注册（已否决）

v1 用共享 token、支持机器注册直落，看似更简单。**否决理由**：v2 是 FR-139/140/141 的身份状态机入口，退役即放弃「首次接入人工确认」与身份冲突处置（FR-141）；且 v2 的 namespace token 是 FR-142 强隔离的凭据载体，v1 的共享 token 无法替代。此外会让「新 agent 必须有唯一身份」这一 FR-139 结论失去执行点。

### 方案 B：退役 v1 的注册职责，数据面另立路径（已否决）

把注册统一到 v2、v1 只留数据面，看似职责最清晰。**否决理由**：v1 的 `/register` 同时是 FR-222 机器注册的判定落点（`agent_machine_register.go` 明确「机器注册的分支落点是 **v1 注册**」）；移除它等于移除 FR-222 已真机验收通过的能力。且迁移其他数据面端点的收益不足以匹配改动面。

### 方案 C：合并为单端点，按 token 类型分流（已否决）

一个端点内按凭据种类判断走身份状态机还是机器注册。**否决理由**：把两条凭据路径的判定收进同一 handler，会让「调用方类型」这一安全判定与请求处理耦合；FR-222 要求该判定由**中间件**完成且不入请求体，合并会破坏这一边界。

### 方案 D：维持现状，仅补文档（部分采纳）

不改端点名、只写文档。**部分采纳**：本 ADR 采纳其「不改运行时语义」的克制，但**不采纳**「只补文档」——因为「同名」本身是歧义根源，仅靠文档无法在调用点消除（插件代码里两处 `url = "$base/beacon/v{1,2}/agent/register"` 读起来完全一样）。故保留更名（FR-233 决策 2）。

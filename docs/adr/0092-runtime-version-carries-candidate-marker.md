# ADR-0092：运行时版本串携带候选标记与构建提交

**状态**：已接受；部分取代 [ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条（运行时版本报告口径），其余决策承继

## 背景

[ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条要求：从某版本首个 RC 起，**运行时版本、JAR/POM、版本化文件名与 OCI payload 均报告 `X.Y.Z`，不含 `-rc.N`**。该口径服务于两个硬约束——`VERSION` 文件保持可解析、GA 复用最终 RC 的同字节资产。

但这条口径只覆盖了"机器怎么读版本"，没有覆盖"**人怎么认出手上这个二进制是哪个候选**"。实际后果是：

- `beacon --version` 在 `v1.5.0-rc.1` 与 `v1.5.0-rc.2` 上**输出完全相同**（都是 `1.5.0`），启动日志、状态页同样只报 `1.5.0`。
- 唯一的区分依据只剩 GitHub Release 的 `SHA256SUMS.txt`，或比对文件字节大小。二进制一旦离开下载目录（落进部署目录、改名、进容器镜像），就**再也无法自证是哪个候选**。
- 候选验收因此极易把旧候选当成新候选测试：两份二进制名字一样、版本号一样、日志一样，而 rc.1 与 rc.2 恰恰存在**破坏性行为差异**（如 ADR-0090 把 `/metrics` 从主端口移到独立监听），误测代价是发布事故。

需要在不破坏 `VERSION` 解析、不破坏 GA 同字节晋级、不破坏在线更新判新的前提下，让"哪个候选"成为**可直接读出的字面事实**。

## 决策

### 1. 展示串携带候选标记与构建提交

控制面新增两个构建期注入字段，与正式版本号分开存放：

| 字段 | 内容 | 注入来源 |
|---|---|---|
| `Version` | 正式版本 `X.Y.Z`（**不变**） | 根 `VERSION` |
| `Candidate` | 候选标记，形如 `rc.2`；非候选构建为空 | RC tag 反推 |
| `Commit` | 构建来源短提交号（8 位）；无 git 环境为空 | `git rev-parse --short=8 HEAD` |

展示串为 `Version[-Candidate][ (Commit)]`，例：`1.5.0-rc.2 (114cf533)`。`--version` 输出、启动日志、状态页版本字段统一使用该展示串。

### 2. `Version` 字段必须保持三段纯数字，候选标记不得拼入

在线更新判新（`internal/update` 的 `parseSemver` 严格要求三段）与换版对账直接消费 `Version`。把 `-rc.2` 拼进该字段会让**更新检查静默失效、执行更新直接失败**——这是本决策选择"新增独立字段"而非"改版本号字符串"的根本原因。

`VERSION` 文件、`valid_version()` 校验、Maven 坐标、版本化文件名与 GA tag 推导**一律不变**。

### 3. RC 构建期断言展示串

RC 构建在生成二进制后立即校验 `--version` 输出等于 `<Version>-<Candidate> (<Commit>)`，不符即失败。候选标记与提交号由 workflow 从 RC tag 与 commit 推导，不接受人工传入。

### 4. GA 如实显示产出该字节的候选标记

GA 复用最终 RC 的同字节资产、不重建（[ADR-0074](0074-simple-rc-ga-release-flow.md) 第 3 条），因此 GA 的展示串**必然**带着最终候选的标记（如 `1.5.0-rc.2 (114cf533)`）。这是刻意行为：

- 抹掉它需要在 GA 阶段重新构建或改写二进制，直接破坏"晋级不引入新变量"；
- 该标记**如实标明该字节产自哪个候选**，是供应链事实而非版本号错误；
- 用户可见的"正式版本"仍由 Git tag、Release 与 Maven 坐标三处权威表达，展示串不承担该职责。

### 5. 可辨识性不扩展到 JAR/POM、版本化文件名与 OCI payload

本 ADR 只改变**控制面运行时展示串**。agent JAR 名、Maven 坐标、产品文件名与 OCI digest 的正式版本口径维持 ADR-0073 第 4 条不变：它们由构建系统按坐标管理，且候选与 GA 使用同一份字节。给文件名加候选标记会连带破坏资产闭集校验（`expected_asset_names()`）与 GA 原样复制，收益与代价不成比例。

## 与既有 ADR 的关系

1. **部分取代 [ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条**：该条中"运行时版本报告 `X.Y.Z`"收窄为"**`Version` 字段**报告 `X.Y.Z`"；JAR/POM、版本化文件名与 OCI payload 的 `X.Y.Z` 口径原样保留。ADR-0073 其余全部决策（不可变 RC、同字节晋级、GA-only 在线更新、workflow 后置创建 tag）继续有效。
2. **与 [ADR-0074](0074-simple-rc-ga-release-flow.md) 一致**：第 3 条"GA 只复制最终 RC 已发布的产品资产，不重新编译、打包、重建、重签或替换产品文件"正是本 ADR 决策 4 的前提；本 ADR 不引入任何 GA 阶段重建。
3. **与 [ADR-0082](0082-rc-ga-sdk-maven-publication.md) 一致**：其 `X.Y.Z-rc.N` 与 `X.Y.Z` 双坐标发布不受影响——Maven 坐标由构建系统管理，不读运行时展示串。
4. **与 [ADR-0007](0007-versioning-and-release-channels.md) 一致**：`VERSION` 仍是唯一版本源，`Version` 字段仍由它注入。

## 理由

1. **机器可读与人可读分离**：正式版本号是机器契约（更新判新、坐标、tag 推导），候选标记是人可读事实。两者合一会让其中一个必然失效，分开则各自成立。
2. **成本极低且无新依赖**：两个 `-ldflags -X` 变量 + 一个纯函数拼接，不改数据模型、不加配置项、不引构建工具。
3. **可验证**：RC 构建期断言使"输出能分辨"成为发布门禁的一部分，而非事后人工确认。
4. **诚实优先**：GA 显示产出它的候选标记，比显示一个与字节不符的"干净"版本号更符合供应链可审计目标。

## 后果

### 正面

- 同一正式版本的不同候选，`--version`、启动日志、状态页**一眼可辨**，无需哈希或大小比对。
- 提交号同时解决了"这个二进制是从哪个 commit 构建的"——此前该信息在运行时完全不可得。
- `Version` 字段的机器契约与在线更新链路零改动，已发布 RC 的行为不受影响。

### 约束

- GA 的展示串会带最终候选标记，需要在运维与用户沟通中说明"这是字节来源，不是版本号错误"。
- 发布构建若缺失 git 元数据（如源码包解压），提交号为空、展示串退回 `X.Y.Z`；不阻断构建，但该形态不具备候选辨识能力。

## 否决方案

### 方案 A：把 `-rc.N` 拼进 `Version` / `VERSION` 文件

`parseSemver` 严格要求三段、`valid_version()` 拒绝四段以上，在线更新会静默失效（检查按"无更新"处理、执行直接失败）。同时 Maven 坐标与 GA tag 推导都会失配。否决。

### 方案 B：给 GA 阶段改写或剥离候选标记

需要对 RC 字节做二进制改写或重新构建，直接违反 ADR-0074 第 3 条"晋级不重建"与 ADR-0073 第 6 条。且改写后的字节与 RC 不再逐字节相同，`SHA256SUMS.txt` 校验必然失败。否决。

### 方案 C：给产品文件名加候选标记

会破坏 `expected_asset_names()` 资产闭集校验与 GA 原样复制（GA 文件名须与 RC 完全一致）。且文件名对"正在运行的实例"不可见——运维看的是进程与日志，不是文件名。否决。

### 方案 D：维持现状，靠 `SHA256SUMS.txt` 外部比对

二进制离开下载目录即无法自证，验收时误测旧候选的代价是发布事故。把可辨识性寄托在"操作者记得保留清单"上不可接受。否决。

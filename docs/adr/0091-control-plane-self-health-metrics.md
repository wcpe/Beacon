# ADR-0091：控制面自身健康进抓取端点（DB 查询留在后台，抓取只读缓存）

**状态**：已接受

> 本 ADR **扩展 [ADR-0090](0090-metrics-endpoint-dedicated-listener.md)**：沿用其「独立监听 + 可选 Bearer 鉴权」的全部约定，只在其端点上新增加一类此前没有的指标（控制面进程自身健康）。ADR-0090 的正文与状态保持不变。

## 背景

控制面的「自身健康」此前只有一个出口：管理台的 `/admin/v1/system/observability` 页面（FR-82）。它聚合四类进程内部运行态——数据库连接池统计、长轮询四通道挂起数、注册表规模、命令队列深度，另有指标异步写入的累计丢弃行数（FR-144）。

问题在于**这个出口监控系统够不到**：该端点在管理面鉴权链之内（挂 `adminAuthMiddleware`），而 Prometheus 只会抓 `/metrics`，不会持管理台登录令牌去请求它。于是这些信号只能靠人登录管理台肉眼查看——而它们恰恰是**故障前兆**：

- **连接池等待**（`WaitCount` / `WaitDuration`）持续增长意味着池正在枯竭。生产事故 2026-10-10 的直接形态就是池被占满后「所有需 DB 的端点挂起」，而当时运维在指标上看不到任何前兆。
- **命令队列积压**是 429 背压出现**之前**唯一的信号。OPERATIONS 早已记录这个缺口：「429 出现前运维从指标上看不到积压」。
- **指标写入丢弃**（`MetricWriteDiscarded`）非零意味着数据**已经丢了**——多次重试仍失败才计入，这是最该告警的一类。

即：控制面自身的健康在监控上完全不可见，只能靠人在出事后登录页面回溯。这与 [ADR-0090](0090-metrics-endpoint-dedicated-listener.md) 修掉的那类问题同源——**信号存在，但到不了监控系统**。

## 决策

在抓取端点上新增控制面自身健康指标，前缀 `beacon_self_`（与描述被管实例的 `beacon_instances_*` 区分开）。

指标清单：

| 指标 | 类型 | 标签 | 含义 |
|---|---|---|---|
| `beacon_self_db_pool_connections` | gauge | `state`（max_open/open/in_use/idle） | 连接池各状态连接数 |
| `beacon_self_db_pool_wait_total` | counter | — | 累计等待连接的次数（池枯竭的直接信号） |
| `beacon_self_db_pool_wait_duration_seconds_total` | counter | — | 累计等待连接的总时长 |
| `beacon_self_longpoll_waiters` | gauge | `channel`（config/file/topology/command） | 长轮询各通道挂起 waiter 数 |
| `beacon_self_commands` | gauge | `status` | 命令队列深度 |
| `beacon_self_metric_write_discarded_total` | counter | — | 指标异步写入累计丢弃行数 |
| `beacon_self_commands_snapshot_timestamp_seconds` | gauge | — | 命令队列缓存最后一次成功刷新的 Unix 秒 |
| `beacon_self_write_queue_depth` | gauge | `route` | 异步日表写入通道各路由的队列深度（429 背压出现前的预警信号） |
| `beacon_self_write_queue_capacity` | gauge | — | 各路由队列容量，与 depth 相除得水位占比 |

**核心约束：抓取路径不触达 DB。**

命令队列深度源自一次 `SELECT status, count(*) GROUP BY status`（`AgentCommandRepository.CountByStatus`）。若在抓取时执行它，由于抓取端点默认无鉴权且**不设限流**（ADR-0090 明确本批不加），任何能访问该端口的人都能按任意频率驱动数据库查询——等于把 DB 负载交给外部请求速率决定。这与 ADR-0090 的初衷（收敛暴露面）方向相反。

故按数据来源拆两条路：

1. **内存类字段抓取时现读**：连接池统计（`sql.DBStats`，标准库自带锁）、长轮询挂起数（Hub 内部加锁）、丢弃计数（原子读）。这些进程内立即可得，现读比缓存更准（不会滞后一个刷新周期）。
2. **DB 类字段后台周期刷新**：命令队列深度由 `commandCountRefresher` 每 15s 采集一次写入指标缓存，抓取只读缓存。15s 与 Prometheus 默认抓取间隔同量级，既不加重 DB 负担，又足以在积压发展成 429 之前被看到。

**写入队列深度同样属「内存类」**：它读的是有界 channel 的 `len()`（O(1)、并发安全），故抓取时现读、无需缓存。这一条补掉了 OPERATIONS 记录已久的缺口——此前「429 背压出现**之前**运维从指标上看不到积压」，只能等「多次重试仍失败而丢弃」的计数，而那时数据已经丢了。容量一并作为独立指标输出，使水位占比可直接计算而无需在告警表达式里硬编码容量。

管理台 `/system/observability` 的行为不变，仍走 `Snapshot()`（允许实时查库，它是低频人工访问页面）。

## 实测校准（60 服规模，2026-10-14）

在 40 核宿主机上实测 60 台注册 + 五类负载族 × 并发 8/32/128 共 11 档（每档 20s，0 失败，RPS 3103~10235），据以校准告警判据：

- **池等待「次数」不能作判据**：正常负载下等待次数就达 1 万~2 万次/秒，11 个档位横跨 51~20207 次/秒（3 个数量级）。任何固定阈值都会持续误报或完全漏报。
- **池等待「平均时长」可作判据**：`rate(等待耗时) / rate(等待次数)` 实测稳定在 0.00025~0.0099 秒/次，且与 p99 时延正相关（最慢档位 p99 89ms 对应均值 9.9ms）。告警阈值取 50ms，为实测正常上界（约 10ms）的 5 倍余量。
- **等待为 0 时方向安全**：PromQL 的 `rate/rate` 在分子分母同为 0 时得空值，比较运算符返回空、不触发告警——不会把「没有等待」误报成「等待极长」。
- **命令队列阈值未校准**：命令由运维主动操作产生（文件浏览 / 强制重同步 / 取日志 / 拓印确认），不随 agent 流量增长，故该值在压测中恒为 0。阈值属保守起点，调参方向已写入 OPERATIONS。

## 理由

- **抓取频率不可控，DB 查询代价可控**：抓取间隔由监控侧配置、且端点不设限流；把一次 `GROUP BY` 挂在上面，等于让外部决定 DB 负载。后台定频采集把「查询频率」与「抓取频率」解耦，这是本决策的实质。
- **15s 的取舍**：命令队列深度的变化以秒计（agent 拉取/回执），15s 滞后对「积压预警」这一用途足够；而缩短到抓取间隔（常见 15~30s）收益有限，却会让 DB 查询频率随抓取方数量线性增长。
- **内存类不缓存**：连接池与长轮询挂起数都是 O(1) 的进程内读取，缓存反而引入一个不必要的滞后与一致性问题。
- **指标前缀分离**：`beacon_self_*` 与 `beacon_instances_*` 语义正交——前者答「控制面这个进程自己怎么样」，后者答「被它管理的实例怎么样」。混用前缀会让看板与告警表达式难以区分主体。
- **枚举清单本包内维护而非 import model**：metrics 包当前只依赖 `runtime`（保持底层观测包不耦合数据模型）。代价是状态清单需手工同步，故用单测锁定它与 `model.CommandStatus*` 常量一致——漂移会让某状态静默缺失。
- **未知状态照常输出**：不在已知枚举内的状态意味着出现了代码未预期的取值，静默丢弃会让它永远不被发现；输出后看板会直接多出一条 series。

## 后果

- **采集失败不写缓存**：刷新器在查库失败时保留上一轮值（不写空 map）。清空会把「采集失败」伪装成「队列为空」——一个假的好消息，恰好掩盖真问题。配套的 `..._snapshot_timestamp_seconds` 会停在旧时刻，用 `time() - 本值` 即可判断陈旧度，比 series 消失更容易发现异常。
- **启动后前 15s 的时间戳为 0**：若刷新器尚未成功采集，时间戳指标为 0（表示从未成功），而计数输出全 0。这是刻意的可区分设计——运维据时间戳判断「是真空还是没采到」。刷新器首轮**立即**执行（不等第一个 tick），把这个窗口压到最小。
- **多一个后台 goroutine**：随关停信号退出（`Run(ctx)`），与其他后台 worker 同范式。
- **不改管理台行为**：`/system/observability` 仍实时查库，两者数据同源但采集时机不同，个别时刻的数值可能有细微差异（管理台更新，抓取侧滞后最多 15s）。

## 备选方案

- **抓取时直接查库**：实现最简（`Collect` 里调 `CountByStatus`），但把 DB 负载交给外部请求速率决定，且端点默认无鉴权。否决——这正是本 ADR 要避免的形态。
- **给抓取端点加限流，然后允许抓取时查库**：限流是独立关注点（ADR-0090 已明确本批不加），且即便限流也无法阻止一个合法的抓取方把间隔调到 1s。否决。
- **把自身健康暴露在管理台端点、让 Prometheus 持管理台令牌抓**：需要把管理面凭据交给监控系统，且抓取会受管理面鉴权/只读裁决/审计链影响，语义错位。否决。
- **缓存全部字段（含内存类）**：实现更统一，但给 O(1) 的内存读取引入不必要的滞后与一致性负担，且掩盖不了任何问题。否决。
- **不加 `..._snapshot_timestamp_seconds`**：少一个指标，但「队列为空」与「采集失败导致值不更新」将无法区分——而后者正是最需要被发现的形态。否决。

# ADR-0085: MCP 端点接受客户端凭据直连（第二类长期凭据）

- **日期**: 2026-09-29
- **状态**: accepted
- **关联**: FR-219 · 增强 ADR-0080（MCP OAuth Client Credentials）

## 上下文

MCP 端点此前只接受一种 bearer：`mct_` 前缀的短期 access token，固定 15 分钟 TTL，由 `client_credentials` 换取。

对**长驻客户端**（IDE 插件、本机工具）而言，这个 TTL 是持续负担：客户端必须在过期前重新换令牌，而主流 MCP 客户端不支持自定义续期逻辑。实践中的绕法是外挂刷新脚本 + stdio 桥接进程——本机为此长期跑着 `proxy.mjs` 与 `token.sh` 两个额外进程，正是这套绕法的产物。

同时，端点已经无状态化（同批改造）：不再有会话，每个请求独立鉴权。这使「凭据形态」成为唯一的长期状态，也让引入第二类凭据不再牵扯会话生命周期。

## 决策

1. **MCP 端点接受两类 bearer**，按前缀分派：
   - `mcs_` 前缀 → **客户端凭据直连**：bearer 即 client secret 本身；按 `secret_prefix` 取候选、`secret_hash` 常时比对、`status=active` 放行；
   - 其余（`mct_`）→ 维持原短期 token 校验路径，**一行不动**。
2. **不改 TTL、不签发 refresh token**：15 分钟约束与「不签发 refresh token」的规范约束保持不变；直连是与 token 并行的另一条路径，不是对它的放宽。
3. **不放宽其它边界**：直连沿用 HTTP 层既有门禁与限速；鉴权失败同样不区分内部原因（防枚举探测）。
4. **生产必须 HTTPS**：直连模式下 client secret 即长期凭据，明文信道等同凭据泄露。

## 理由

- **消除外挂进程**：客户端凭据可长期持有，长驻客户端因此能直连，刷新脚本与桥接进程整体退场。
- **吊销/轮换天然即时生效**：`revoke` 使 client 转 revoked、`rotate` 改写 `secret_hash` 并递增 `secret_version`，两者都直接作用于校验路径，无需额外失效逻辑。
- **不削弱现有边界**：token 路径未改；两类凭据最终归约到同一 principal 构造与同一能力判定。
- 与无状态化同向：端点不记状态，凭据形态成为唯一的长期事实。

## 后果

- 客户端凭据的**保管责任前移到客户端**：secret 落在客户端配置里（本机为 NarraFork 的 `settings.json`），泄露即长期可用——故生产必须 HTTPS，且应定期轮换。
- 12 字符展示前缀被用于候选查询：前缀本身不足以反推 secret（仍需完整哈希比对），但可被枚举以确认「某前缀是否存在」；该风险由 HTTP 层限速与不区分失败原因吸收。
- 文档面：`docs/API.md`（两类 bearer）、`docs/OPERATIONS.md` §9.2（排障要点）、`docs/specs/built-in-admin-v2-mcp-and-oauth.md` §4.4（凭据形态定义）。
- 运维动作无需新增界面：MCP 客户端管理台（FR-224）已有轮换/吊销，据此定期轮换即可。

## 备选（未采纳）

- **把 TTL 做成可配置**：客户端仍不会自行续期，解决不了长驻客户端的问题，只是把失效时间推远。
- **签发 refresh token**：与既有规范约束（不签发 refresh token）直接冲突。
- **在客户端侧实现自动续期**：要求逐个改造生态内所有 MCP 客户端，把兼容责任推给外部。

## 关系

- **增强 ADR-0080**：不改变其「客户端凭据不落明文、令牌受众固定、撤销/轮换即时阻断后续换令牌」的决策，只增加一类与之并行的长期凭据形态。

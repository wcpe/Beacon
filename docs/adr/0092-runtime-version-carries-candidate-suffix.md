# ADR-0092：运行时版本号携带候选后缀

**状态**：已接受；部分取代 [ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条（运行时版本报告口径），其余决策承继

## 背景

[ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条要求：从某版本首个 RC 起，**运行时版本、JAR/POM、版本化文件名与 OCI payload 均报告 `X.Y.Z`，不含 `-rc.N`**。该口径服务于"GA 复用最终 RC 的同字节资产"这一正确目标。

但它没有覆盖"**人怎么认出手上这个二进制是哪个候选**"。实际后果是：

- `beacon --version` 在 `v1.5.0-rc.1` 与 `v1.5.0-rc.2` 上**逐字相同**（都是 `1.5.0`），启动日志、状态页、更新页同样如此。
- 实测确认：同 commit 下 rc.1 与 rc.2 的二进制**字节大小完全相同**（30912775），因此"看文件大小"也无法区分。
- 唯一依据只剩 GitHub Release 的 `SHA256SUMS.txt`。二进制一旦离开下载目录（落进部署目录、改名、进容器镜像），就**再也无法自证是哪个候选**。
- rc.1 与 rc.2 恰恰可能含破坏性差异（如 [ADR-0090](0090-metrics-endpoint-dedicated-listener.md) 把 `/metrics` 迁到独立监听），验收时误测旧候选的代价是发布事故。

## 决策

### 1. 运行时版本号本身带候选后缀

候选构建注入的运行时版本为 `X.Y.Z-rc.N`（如 `1.5.0-rc.2`）。`--version`、启动日志、状态页、更新页**原样输出该串**，不带括号、不附提交号。

### 2. `VERSION` 文件保持 `X.Y.Z`，仅注入值带后缀

这是本决策的关键分工：

| 用途 | 值 | 说明 |
|---|---|---|
| 根 `VERSION` 文件 | `1.5.0` | 驱动 RC/GA tag 构造、产品资产名、`valid_version()` 校验 |
| 注入二进制的运行时版本 | `1.5.0-rc.2` | 仅用于可读展示与更新判新 |

候选后缀从 RC tag 反推（`vX.Y.Z-rc.N` → `-rc.N`），不接受人工传入。

**不把后缀写进 `VERSION` 文件**，因为该文件驱动多处机械拼接：`prefix="v${VERSION}-rc."` 会产出 `v1.5.0-rc.2-rc.3`、`ga_tag="v${version}"` 会把候选误当 GA tag、`beacon-${version}-…` 会让 GA 资产闭集校验失配。改注入值只需动一处，改 `VERSION` 要动四处拼接且每处都需重新论证。

### 3. 版本比较两侧强度不对称

`IsNewer(current, remote)` 对两个入参采用不同口径：

- **当前版本**按运行时口径解析，**接受**候选后缀——候选实例的版本号就是 `1.5.0-rc.2`，拒绝会让判新解析失败并静默退化为"无更新"。
- **远端版本**按 GA 口径解析，**严格拒绝**候选与开发后缀——在线更新只消费 GA（[ADR-0074](0074-simple-rc-ga-release-flow.md) 第 4 条），放宽会让 `vX.Y.Z-rc.N` 被当成更新候选装进生产实例。

排序遵循 SemVer 2.0.0 第 11 条：`1.5.0-rc.2 < 1.5.0`（候选高于同号 GA 判为有更新，候选实例可正常晋升）、`1.5.0-rc.2 < 1.5.0-rc.3`（候选可逐号升级）、`rc.10 > rc.9`（数字段按数值而非字典序）。

### 4. RC 构建期断言运行时版本串

RC 构建生成二进制后立即校验 `--version` 输出等于注入的运行时版本，不符即失败。可辨识性因此成为发布门禁的一部分，而非事后人工确认。

### 5. GA 会如实报告最终候选的后缀

GA 复用最终 RC 的同字节资产、不重建（[ADR-0074](0074-simple-rc-ga-release-flow.md) 第 3 条），故 GA 安装同样报告 `1.5.0-rc.2`。这是刻意行为：

- 抹掉它需要在 GA 阶段重建或改写二进制，直接破坏"晋级不引入新变量"，且改写后字节与 RC 不再相同，`SHA256SUMS.txt` 校验必然失败；
- 该后缀**如实标明该字节产自哪个候选**，是供应链事实而非版本号错误；
- 版本身份由 Git tag、Release 与 Maven 坐标三处权威表达。

### 6. 可辨识性不扩展到 JAR/POM、资产文件名与 OCI payload

agent JAR 内 `plugin.yml`、Maven 坐标、产品文件名与 OCI digest 的版本口径**维持 ADR-0073 第 4 条不变**：它们由构建系统按坐标管理，且候选与 GA 使用同一份字节。给文件名加后缀会连带破坏 `expected_asset_names()` 资产闭集校验与 GA 原样复制。

## 与既有 ADR 的关系

1. **部分取代 [ADR-0073](0073-standard-rc-ga-release-lifecycle.md) 第 4 条**：该条中"运行时版本报告 `X.Y.Z`"收窄为"**`VERSION` 文件与产品资产名**报告 `X.Y.Z`"；运行时版本号改为携带候选后缀。JAR/POM、文件名与 OCI payload 口径原样保留，其余全部决策（不可变 RC、同字节晋级、GA-only 在线更新、workflow 后置创建 tag）继续有效。
2. **与 [ADR-0074](0074-simple-rc-ga-release-flow.md) 一致**：其第 3 条"GA 只复制最终 RC 已发布的产品资产，不重新编译、打包、重建、重签或替换产品文件"正是本 ADR 决策 5 的前提；本 ADR 不引入任何 GA 阶段重建。
3. **与 [ADR-0082](0082-rc-ga-sdk-maven-publication.md) 一致**：Maven 坐标由构建系统管理，不读运行时版本串，其 `X.Y.Z-rc.N` 与 `X.Y.Z` 双坐标发布不受影响。
4. **与 [ADR-0007](0007-versioning-and-release-channels.md) 一致**：`VERSION` 仍是唯一版本源，运行时版本由它派生。

## 理由

1. **版本号本来就该说得清楚**：一份候选二进制报告自己的真实身份是最小惊讶原则；要求它对外谎报成正式版，是把"GA 复用字节"的实现细节泄漏成了对使用者的误导。
2. **改动面小**：只需放宽解析器接受候选后缀、注入值加后缀、GA 侧显式拒绝后缀三处；`VERSION` 文件与全部发布脚本零改动。
3. **安全边界不放松**：远端严格只认 GA 的口径未变，候选不会因本次放宽而进入自动更新候选集。
4. **可验证**：构建期断言使"输出正确"成为门禁。

## 后果

### 正面

- 同一正式版本的不同候选，在 `--version`、启动日志、状态页、更新页**一眼可辨**，无需哈希或文件大小比对。
- 候选实例能正常判新：既能升级到同号 GA，也能升级到更高序号候选。
- `VERSION` 文件与发布脚本零改动，已发布的 GA 晋级链路不受影响。

### 约束

- GA 会报告最终候选后缀，需在运维沟通中说明"这是字节来源，不是版本号错误"。
- 解析器需要维护两侧不同强度，改动该函数时必须同时核对"当前侧放宽、远端侧收紧"这一不对称性——相关测试已锁定。

## 否决方案

### 方案 A：保持纯 `X.Y.Z`，靠 `SHA256SUMS.txt` 外部比对

二进制离开下载目录即无法自证；实测证明字节大小也相同，等于把可辨识性完全寄托在"操作者记得保留清单"上。验收误测旧候选的代价是发布事故。否决。

### 方案 B：把后缀写进 `VERSION` 文件

会连锁破坏四处机械拼接：RC tag 变成 `v1.5.0-rc.2-rc.3`、GA tag 变成 `v1.5.0-rc.2`、资产名带后缀与 GA 资产闭集校验冲突、`valid_version()` 拒绝四段以上。否决。

### 方案 C：运行时版本带后缀，但另存一份纯版本号供判新

需要同时维护两个字段并在每处判断该用哪个，是"方案 B 的一半加上额外的一致性负担"；而解析器本就可同时处理两种形态。否决。

### 方案 D：给 GA 阶段剥离后缀

需对 RC 字节做二进制改写或重建，违反 ADR-0074 第 3 条，且改写后字节与 RC 不同，`SHA256SUMS.txt` 校验必然失败。否决。

### 方案 E：宽松接受远端候选后缀

会让 `vX.Y.Z-rc.N` 成为合法更新候选，把候选装进生产实例，破坏"在线更新只消费 GA"。否决。

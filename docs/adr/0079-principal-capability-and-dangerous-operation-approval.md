# ADR-0079：统一管理主体、语义能力与危险操作审批执行模型

**状态**：已接受（2026-07-29；部分取代 [ADR-0026](0026-runtime-api-keys-and-readonly-role.md) 的两级角色、纯 HTTP 方法判权及拒绝细粒度能力结论）

## 背景

Beacon 当前管理面只有登录操作者与 `full/readonly` API key，两级角色主要按 HTTP 方法区分读写。该模型无法正确识别有副作用的 GET、同一路由中由请求内容决定风险的动作、后台执行器或未来 MCP 工具；`full` 机器凭据还可能直接调用身份和交付审批端点，绕过“机器只能申请、不能审批”的安全边界。

现有高风险操作分散在 Agent 身份、拓扑、配置、文件、交付、系统更新等领域，交付 ChangeOrder 又有自己的审批状态机。新增归档、永久删除与外部 Agent 自动化后，需要一套统一授权内核和可恢复的审批执行模型，同时保留各领域自身不变量，避免复制多套审批状态机或通过内部 HTTP 回调产生递归审批。

## 决策

### 1. 统一 Principal 与语义 Capability

认证完成后统一产生不可伪造的 `Principal`，至少包含：

- `human`：管理台登录的人类操作者；
- `api_key`：现有运行时 API key；
- `mcp`：OAuth client 映射的外部 Agent；
- `system`：控制面内部登记的系统任务。

授权按语义 capability 与 operation descriptor 判定。旧 `full/readonly` 只作为兼容 capability bundle：`readonly` 映射只读能力，`full` 映射现有管理能力，但任何机器 bundle 都不包含审批能力。HTTP 方法不再是充分的风险判据。

### 2. 所有管理操作必须语义分类

每个管理面 REST 路由、MCP tool、后台任务与内部危险执行入口都必须登记为：

- `direct`：可直接执行，仍按 capability 校验并审计；
- `approval_required`：只能冻结并创建审批申请，未取得执行许可不得产生业务副作用；
- `system_exempt`：仅允许明确登记的低风险内部维护策略调用，并记录策略名和执行证据；不得对应危险目录或任何 `approval_required` operation。

分类必须覆盖 `/admin/v1` 与 `/admin/v2` 同义入口、有副作用的 GET、由 body 字段区分风险的操作以及非 HTTP 后台任务。新增入口未分类时，覆盖测试失败并且运行时 fail-closed。

### 3. 只有 human 可以审批，且允许本人自批

- `human` 可提交、审批或拒绝申请，并允许审批本人提交的申请。
- `api_key`、`mcp`、`system` 在服务层一律没有 approve capability；即使伪造 REST、MCP 或内部调用也必须被拒绝。
- 外部自动化可提交、查询和在待审状态撤回自己的申请，但不能批准任何申请。
- 降低权限或立即止损的动作可 `direct + 强审计`，包括吊销凭据/信任、禁用身份、暂停或取消运行中任务；重新授权、启用、恢复、重新启动或扩大影响仍需审批。

### 4. 审批申请冻结意图与影响事实

申请至少持久化：`approvalRequestId`、operation、申请主体、原因、目标引用、规范化参数摘要、脱敏参数、影响快照、资源版本/冻结哈希、风险级别、创建时间与固定 24 小时过期时间。申请内容创建后不可修改。

状态至少区分：`pending`、`withdrawn`、`rejected`、`expired`、`executing`、`succeeded`、`failed`。撤回只允许申请人在 pending 时执行；拒绝、过期或执行失败均为终态，需要重新提交。历史记录永久可查，不因完成而消失。

### 5. 批准即交给持久执行器

human 的“批准并执行”是一个服务端动作：原子记录批准事实与可执行任务，随后由数据库驱动的进程内 worker 认领执行。worker 使用幂等键、CAS/lease 与有限重试，控制面重启后可恢复；不引入 Redis、MQ 或第二进程。

执行前必须重新校验领域不变量、当前资源版本、影响快照漂移与冲突。漂移或领域守卫失败时记录 `failed`，不得自动扩大批准范围。批准成功但执行失败必须同时保留批准事实和失败原因，不能回写成“未审批”。

### 6. ExecutionPermit 封死服务层旁路

危险领域方法必须接收仅由审批执行器构造的进程内 `ExecutionPermit`。普通 HTTP handler、MCP handler、system policy、定时任务和测试外部输入都不能构造该许可。`system_exempt` 使用与 ExecutionPermit 分型的内部策略证据，只能调用低风险维护方法；危险后台任务只能消费已获 human 批准的持久任务。审批执行器直接调用领域 adapter，禁止回调原 REST 路由，也禁止领域 adapter 反向依赖审批具体实现。

Agent 身份、ChangeOrder 等既有领域状态机继续拥有自己的状态与事务不变量；通用审批通过 adapter 授权领域转换，不再叠加第二次领域审批。ChangeOrder 的 human 批准应直接进入持久自动启动路径，不再要求另一个公开 start 权限步骤。

### 7. 审批证据与审计必须 fail-closed

申请、批准/拒绝、任务认领、执行结果和失败原因与审批真源在事务内持久化；审计兜底中间件不能代替审批证据。日志、参数快照和审计不得保存 token、secret、敏感文件明文或消息 payload，错误按既有脱敏规则对外可见。

## 理由

- 语义 operation 能覆盖 GET 副作用、body 分支与后台任务，避免方法级权限的结构性漏口。
- 机器主体在服务层无审批能力，外部 Agent 即使同时能调用 REST 也无法绕过人审。
- 数据库驱动执行器满足单进程架构与重启恢复，不需要引入重型中间件。
- ExecutionPermit 把审批约束放在真正产生副作用的 service 边界，不依赖所有调用者自觉。
- 领域 adapter 保留身份、排空、交付等既有不变量，避免通用审批内核演化成上帝服务。

## 后果

- 现有登录、API key 与未来 OAuth 认证都要映射为统一 Principal；审计需 additive 增加主体类型与主体 ID。
- 管理路由和领域操作需要完整清点并登记语义分类，V1/V2 同义入口必须指向同一授权路径。
- 交付与身份现有审批入口需要改为通用审批 adapter，保留领域读模型但不得出现双审批。
- 审批中心与 MCP 只消费统一申请模型和 operation descriptor，不维护自己的状态真源。
- [ADR-0026](0026-runtime-api-keys-and-readonly-role.md) 关于 API key 哈希、明文仅一次、吊销即时生效等决定继续有效；其两级角色作为最终授权模型、纯 HTTP 方法判权和拒绝细粒度 capability 的结论由本 ADR 部分取代。

## 备选方案

- **继续按 HTTP 方法判断风险**：无法覆盖副作用 GET、body 分支和内部任务。否决。
- **为每个领域复制一套审批表与状态机**：状态、过期、审计和执行恢复会漂移。否决。
- **MCP 只是不暴露审批按钮，但服务层仍允许机器审批**：可被普通 REST 或伪造调用绕过。否决。
- **批准后由申请方再次调用 execute**：产生“已批但无人执行”或重放窗口，不符合批准即执行。否决。
- **审批执行器 HTTP 回调原路由**：会递归创建审批或依赖路由绕过开关。否决。
- **引入外部消息队列**：本规模与单进程架构不需要，增加部署和一致性成本。否决。

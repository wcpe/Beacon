# ADR-0095：控制面可下发 agent 运行配置，但接入目标与身份永远留在本地

**状态**：已接受（2026-10-21；推翻 [ADR-0011](0011-delivery-override-hot-reload.md) 决策 3 中「命令首 token 白名单放 agent 本地、不由控制面下发」一条，其余约束不变）

## 背景

agent 的运行参数此前只能写在每台服的 `config.yml` 里。60 台服务器意味着同一项配置要重复 60 次，且**新增一台就要再配一遍**；漏配不会报错，只会让那台服的行为与其它服不一致（例如 `override.command-whitelist` 为空时该服静默不执行任何重载命令，而控制面上看不到差别）。

把配置收敛到控制面统一下发，是这个规模下的必然选择。但它改变了信任模型：**控制面变成了 agent 运行参数的权威来源**，于是"控制面能改什么"成了必须回答的安全问题。

同时，[ADR-0011](0011-delivery-override-hot-reload.md) 决策 3 明确禁止下发命令白名单，理由是「控制面被攻破也无法越白名单提权」。本次需求方判断部署形态为**内网可达**，要求白名单也纳入下发，以消除逐台配置的重复劳动。

## 决策

1. **建立 agent 配置下发通道**（`GET /beacon/v2/agent/settings` + `GET/PUT /admin/v2/agent-settings`），支持 `namespace` 级默认与 `server` 级覆盖，server 级优先。

2. **推翻 ADR-0011 决策 3 的「白名单不下发」**：`override.command-whitelist` 允许由控制面下发。**该决策以「Beacon 控制面与面板仅内网可达、外网不可达」为前提**；一旦部署形态变化（暴露公网），该条款必须重新评估。

3. **ADR-0011 的其余约束一律不变**：禁 shell、禁注入元字符与管道、单条命令、路径限死（Path 级 `normalize().startsWith`）、禁 `.jar` 与 server 关键文件、备份与回滚不重放命令。这些是"允许执行命令"这件事本身的前提，不是可选项。

4. **新增反向禁区：接入目标与身份永远只能本地决定**。以下键**禁止**由控制面下发：
   - `beacon.endpoints`（改了 = 把 agent 指向另一个控制面，目标劫持）
   - `beacon.bootstrap-token`（改了 = 换身份或让 agent 失联）
   - `identity.*`（身份字段只能由注册/审批流程权威回填，走配置旁路会与主流程打架）

   该禁区在 **agent 侧与服务端各实现一次**（双保险）：agent 侧 `PushedConfigPolicy`，服务端拉取端点独立再挡并落审计。任一侧被绕过，另一侧仍能兜住。

5. **三层优先级写死**：Web 下发 > 环境变量 > `config.yml` > 代码默认。

6. **下发值必须落盘缓存**（`pushed-config.json`）。控制面权威不等于随时可达；断连时若退回代码默认，会出现"重载超时从 30s 悄悄变回 0"这类静默降级。缓存语义是**最后一次已知的权威值**，断连时继续用它工作。

7. **敏感文件与配置分文件存放**，避免混用：
   - `config.yml` — 运维手写部署参数（离线兜底）
   - `agent-credentials.json` — 身份（地址 + 令牌），权限尽力 0600
   - `pushed-config.json` — 下发值（最高优先级）

   分开的直接收益是"这个值是哪来的"永远可回答。凭据不进 `config.yml`，因为后者会被纳入版本管理、被模板复制分发——混进去等于把 token 扩散出去。

## 理由

- **为什么现在可以下发白名单**：ADR-0011 定该条款时的威胁模型是"控制面被攻破即 RCE"。在内网部署下，控制面被攻破的前置条件已是内网沦陷，此时攻击者能做的远不止改白名单。把这条风险显式记录，比继续维持"逐台手配"这种必然漏配的实践更安全——**漏配导致的静默不一致是确定性风险，而下发是显式风险**。
- **为什么要设反向禁区**：下发通道让控制面能改 agent 行为，但**不能让它能改 agent 听谁的话**。若 `beacon.endpoints` 可下发，一个被攻破的控制面可以把全部 agent 重定向到自己的服务器，之后所有配置、所有交付命令都归攻击者——这比"执行白名单内命令"严重一个量级。故禁区不是保守，是防止下发通道把提权面从"执行命令"扩大到"接管身份"。
- **为什么双保险**：agent 是最终权威（与 ADR-0011 "agent 为最终权威"一致）。服务端也挡，是为了让"Web 上误设了禁区键"当场被拒绝并留痕，而不是等 agent 拉到之后静默忽略。
- **为什么缓存要落盘**：下发配置的价值在断连时才真正体现。只在内存等于"控制面一抖，全部 agent 回到出厂默认"。
- **为什么未知键在 agent 侧放行、服务端拒绝**：agent 侧放行是为了前向兼容（新控制面下发老 agent 不认识的键，老 agent 忽略而不是报错，符合协议加性）；服务端拒绝是为了让"键名拼错"当场暴露，而不是变成一条永远不生效的配置。

## 后果

- **控制面被攻破的影响面扩大到「可执行任意白名单内命令」**，前提是部署为内网可达。公网部署必须重新评估本决策第 2 条。
- 新增一台服不再需要任何本地配置（除首次 `join`），运维从"逐台配 N 次"变成"配一次"。
- 新增 agent 配置项时，若要支持下发，需同时在控制面元数据表登记；否则服务端会拒绝（agent 侧仍可用 `config.yml` 配）。
- `override.command-whitelist` 的下发变更**必须**走审批并留审计（`agent-settings.update`），Web 面板对其显示高危警告。
- 断连期间配置变更不生效，且**没有"待生效"提示**——agent 侧只能看到缓存里 `fetchedAt` 的时间。这是已知局限。

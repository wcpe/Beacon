# ADR-0068：文件资产清单上报协议（增量 delta + 摘要校准 + 全量分片兜底）

**状态**：已接受（随 P8 FR-163 落地）。规格 [v2-file-assets.md](../specs/v2-file-assets.md) §4.3/§8 风险 1 记「上报协议选型待拍板」，本 ADR 即该拍板记录。

## 背景

文件资产索引（FR-163）由 agent 周期扫描本机 `plugins/` 与根配置白名单，把「每文件路径 / sha256 / 大小 / mtime」清单上报控制面，控制面只存每服最新快照供搜索 / 跨服比对。1000+ 子服、每服约 2000 文件（上限 50000）。

关键观察：**稳定运行期清单变化极小**，多数扫描周期为零变更。若每周期都全量上报（2000 行 × 1000 服），对控制面是无谓的写放大与事务压力。但纯增量又需要两侧对同一基线达成一致，否则会静默漂移。规格 §4.3 把「上报协议」标为待拍板项，列出三条候选：纯全量快照、增量 diff、双向 Merkle 对账。

## 决策

**采用「增量 delta 为主 + 摘要（digest）校准锚点 + 全量分片兜底」。**

1. **清单摘要算法（两侧同源）**：清单条目按 `path` 字节序升序排列，每条拼接字符串 `path + "\n" + sha256 + "\n" + size + "\n" + mtime_ms + "\n"`，把全部条目拼接后取整体 UTF-8 字节的 sha256 小写十六进制。agent 与控制面用**完全相同**的算法：摘要相等即两侧清单逐字节一致。摘要是增量协议的校准锚点，存 `file_asset_scan.manifest_digest`。

2. **增量上报（`mode=delta`）为默认**：agent 携带 `baseDigest`（它认为控制面当前持有的摘要）+ `upserts[]`（新增 / 变更文件）+ `deleted[]`（消失文件路径）。控制面在**单事务**内：校验 `baseDigest == file_asset_scan.manifest_digest`，一致才应用（批量 upsert + 按路径删除 + 重算摘要 + 刷新概要行），返回控制面**重算**出的新摘要（不信任 agent 自报的新摘要，避免 buggy agent 毒化锚点）。agent 比对返回摘要与本地期望，不一致则下次转全量自愈。

3. **基线失配即退全量**：`baseDigest` 与库中摘要不一致 → 返回 `409 asset_manifest_out_of_sync`，agent 立即改发全量。这是增量协议的收敛保证——**任何漂移都由一次全量强制归零**，不引入复杂的双向对账 / Merkle 树。

4. **全量上报（`mode=full`）为兜底**：首次接入、本地缓存缺失 / 损坏、409 后、`force` 重扫后使用。单请求条目上限 2000，超限分片：agent 生成 `uploadId`，按 `seq` 从 0 递增分批发送，末批 `eof=true`。控制面按 `uploadId` **进程内内存暂存**分片（TTL 5 分钟，过期或 seq 不连续即丢弃并 409 令 agent 重来），收齐（eof）后**单事务整体替换**该服全部 `file_asset` 行并刷新概要。替换是原子事务，全量期间旧快照持续可查。

5. **零变更不发请求 + 保活空 delta**：agent 本地新摘要 == 已确认摘要即整周期跳过上报；仅每 6 个周期发一次空 delta（无 upserts / deleted）刷新概要行的 `scanned_at`，让页面「最近扫描时间」不至于长期停滞。

6. **同服串行 + 幂等**：同一 server 的上报由 agent 单飞串行；摘要乐观校验天然拒绝并发交叉写。重复发送同一 delta（摘要已推进）会 409 转全量，最终收敛，无脏数据。

7. **常规同步事务，不引异步队列**：请求分片已限 2000 条、单事务毫秒级，直接同步入库（区别于指标批量入库的异步日表基调——清单写入频度低得多）。**内存暂存是进程内 map + 锁，非 Redis / MQ**，不违反 [architecture-invariants](../../.claude/rules/architecture-invariants.md) §2。

8. **命令通道复用 [ADR-0006](0006-rest-long-poll-push.md)**：手动重扫 `asset-rescan` 经既有长轮询命令通道下发（`force=true` 令 agent 忽略本地 mtime 缓存全部重哈希），非独立端点。

## 理由

- **写放大最小**：稳定期零变更周期不写库、不发请求；只有真变更才携带最小 delta。相较纯全量每周期 2000 行 × 1000 服，控制面写压降到近乎为零。
- **收敛简单**：摘要作单一锚点，「失配即退全量」用一条最朴素的兜底覆盖所有漂移场景，无需 Merkle 树 / 分块对账 / 版本向量等复杂机制（本规模不值当）。
- **权威在控制面**：新摘要由控制面从落库结果重算，agent 自报摘要仅作本地自检，避免坏 agent 污染基线。
- **原子可查**：全量替换在单事务内完成，读侧永不看到半截清单（满足验收 §3「全量分片原子性」）。

## 后果

- **控制面新增**：`file_asset` / `file_asset_scan` 两表（不分片、不分日期表，200 万行量级单表 + 索引可承载）、agent 面 `POST /beacon/v2/agent/assets/manifest` 端点、进程内全量分片暂存（有界、按 TTL 与 eof 清理）、`asset_manifest_out_of_sync` 错误码。
- **可靠性取舍**：全量分片暂存在控制面进程内存，控制面重启会丢弃未收齐的分片，agent 下个周期重传（接受这一窗口，不落临时表）。
- **agent 侧本地状态**：agent 持久化 `asset-manifest.json`（上次成功上报的清单 + 控制面确认摘要），重启后可继续增量；缓存缺失 / 损坏则回退全量（fail-static：控制面不可达时扫描照常、上报静默等下周期）。
- **与 P9 复用**：清单协议字段（path/sha256/size/mtimeMs）即 P9 变更单模板源差异扫描的数据契约，P9 不另建一套清单（见 [v2-file-assets.md](../specs/v2-file-assets.md) §6）。

## 备选方案

- **纯全量快照每周期上报**：实现最简，但稳定期写放大严重（2000 行 × 1000 服 × 每 30 分钟），且大服全量 JSON 载荷可观。**否决**（写放大不可接受）。
- **双向 Merkle 树 / 分块对账**：能在超大清单下增量定位差异，但对 2000~50000 行量级是过度设计，引入树维护 / 分块协议复杂度，不符简单优先。**否决**（当前规模不值当）。
- **全量分片落临时表暂存**（而非进程内存）：可跨控制面重启续传，但需建临时表 + 清理 job，为一个 5 分钟窗口的边缘收益增持久态。**否决**（接受重启丢分片、下周期重传）。
- **agent 自报新摘要、控制面直接存**：省去控制面重算，但把基线权威交给 agent，坏 agent 可毒化锚点致后续 delta 全部失配。**否决**（权威须在控制面）。

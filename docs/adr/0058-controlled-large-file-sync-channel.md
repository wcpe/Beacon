# ADR-0058：受控大文件同步通道（控制编排与流式数据分离）

**状态**：已接受

## 背景

FR-129~FR-133 要在管理台新增“多级灰度配置同步中心”：运维可选择一台在线 bukkit 子服作为黄金模板源，把某个服务器根内相对目录同步到 1000+ 台 bukkit 子服，并按大区 / 小区 / 单服微调做灰度分批发布。该能力要求同步 `.jar`、地图、资源包等二进制大文件，且必须支持增量哈希比对、本地备份、一键回滚、暂停 / 继续 / 终止和熔断。

现有反向抓取与配置工作台通道（ADR-0027、ADR-0037、ADR-0049）面向 `plugins/` 下文本配置：禁止 `.jar` / 二进制，内容经 JSON 回传，单文件和单次总量都有硬上限。这套边界适合配置纳管，不适合作为大文件分发通道。若把大文件塞进 `agent_command.payload`、审计 detail 或 JSON ingest，会破坏内存、数据库、审计与命令生命周期边界。

## 决策

1. **控制通道与数据通道分离**。`agent_command` 只承载任务编排控制：扫描、上传、下载、备份、回滚、暂停、继续、终止、回执等状态迁移。文件内容不进入命令 payload、命令 result、审计 detail 或 JSON ingest。

2. **新增流式 HTTP 数据通道**。大文件内容通过 agent 主动访问控制面完成流式上传 / 下载：源 agent 流式上传到控制面，目标 agent 分批流式拉取。上传、下载、落盘均必须用流式 IO，禁止把单个大文件整体读入内存。

3. **控制面作为中转缓存**。控制面允许把源 agent 上传的 blob 落到本地磁盘缓存，并记录 size、hash、相对路径、保留期、任务归属等元数据。1000+ 目标从控制面缓存拉取，避免反复打源服务器。缓存清理由后台保留期策略处理。

4. **允许二进制大文件，但只在本同步通道内允许**。`.jar`、地图、资源包等二进制文件可通过本通道同步；该放开不改变 ADR-0027/0037/0049 对反向抓取 / 配置浏览的文本配置边界。换言之：配置纳管仍禁 jar / 二进制，本模块是单独的受控文件同步能力。

5. **路径范围为服务器根内任意相对目录**。运维可选择服务器根目录下任意相对目录；agent 必须拒绝 `..`、绝对路径、盘符、UNC、保留设备名和符号链接逃逸。最终解析路径必须仍在 agent 声明的服务器根目录内。源目录和目标目录固定同相对路径，不做路径映射。

6. **目标仅限 bukkit 子服**。控制面目标筛选只允许 `role=bukkit` 实例，排除 BungeeCord 代理。拓扑筛选可用环境 / 大区 / 小区 / serverId，BC 只作为拓扑分组事实，不作为同步目标。

7. **增量比对在目标侧执行**。源 manifest 记录路径、size、hash、mtime 等事实；目标 agent 同路径扫描本地 manifest 后只下载 hash 不同或缺失的文件，未变化文件直接跳过。

8. **覆盖前本地备份，回滚由 agent 执行**。目标 agent 写入前把目标相对目录重命名为带时间戳备份目录，并向控制面回传备份点。回滚按任务、批次或单服下发回滚命令，由目标 agent 将备份目录恢复到原路径。

9. **浏览器实时进度使用管理台 SSE**。现有 agent SSE 仍只服务 agent。管理台新增独立 SSE 进度流，向浏览器推送任务、批次、目标、日志事件；禁止用短轮询替代实时进度。

10. **状态真源落 DB，运行调度可在进程内**。同步任务、批次、目标、文件清单、缓存对象、备份点、日志摘要和回滚状态必须持久化；调度器可进程内运行，重启后可从 DB 恢复查看与继续处理未终结状态。不得引入 Redis、MQ、DI 框架。

11. **事务与唤醒边界**。状态更新、审计和持久化写入必须在 DB 事务内原子完成；事务提交后再唤醒 agent 或管理台 SSE。文件流本身不得在 DB 事务中执行。

## 理由

- `agent_command` 是可靠的控制原语，不是数据承载层。把大文件从命令表和 JSON 请求中剥离，可以保住命令生命周期、审计、DB 可移植与内存上限。
- 控制面缓存能把源服务器压力从“每个目标都读源”降为“源上传一次、目标分批拉取”，也便于暂停、重试、历史回滚和页面刷新恢复。
- 只在本模块放开二进制，避免污染既有配置纳管边界。配置中心仍是文本配置 / 受管文件模型；同步中心是受控文件分发模型。
- 保持 agent 出站模型，不给 Minecraft 服务器新增入站端口，符合现有网络与安全边界。
- 管理台 SSE 单独建流，避免把浏览器需求混入 agent 的 server→agent SSE。

## 后果

- 新增同步任务相关表、控制面服务、后台调度器、缓存目录和清理器。
- 新增 agent 流式上传 / 下载 / 备份 / 回滚能力，双端 jar 需重建并真机部署。
- 新增 admin API、agent API 和浏览器 SSE 端点，需同步 `docs/API.md` 与 `docs/ARCHITECTURE.md`。
- 新增路径安全、流式 IO、并发状态机、缓存清理、熔断与回滚测试。
- 旧 agent 不具备该能力；控制面必须在任务创建或开始时校验目标 agent 能力版本，不得对旧 agent 下发大文件同步命令。

## 备选方案

- **把文件内容塞进 `agent_command` 或 JSON ingest**：实现快，但会放大内存占用、撞 TEXT/JSON 边界、污染审计与命令表，无法承载大文件。否决。
- **源 agent 对每个目标实时转发**：控制面不落盘，但 1000+ 目标会反复压源服，暂停 / 重试 / 熔断 / 回滚也难以恢复。否决。
- **SSH/SFTP 直接推送**：绕过 agent，但项目当前没有现成 SSH/SFTP 工具类，也会新增凭据管理和入站连接面。用户已确认使用 agent 模型。否决。
- **只同步文本配置**：可复用现有反向抓取，但不满足同步 jar、地图和资源包的需求。否决。
- **给 agent 开 HTTP server 供控制面拉取**：看似直接，但新增入站端口和鉴权面，违背 agent 只出站模型。否决。

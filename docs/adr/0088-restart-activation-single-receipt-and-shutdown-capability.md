# ADR-0088：restart 生效的单次回执收敛与关服能力探测（取代 ADR-0070 决策 2 的回执顺序描述）

**状态**：已接受（决策）；实现并入 FR-266，本批已落地

> 本 ADR **取代 [ADR-0070](0070-agent-graceful-shutdown-primitive.md) 决策 2 中「目标 agent 收到 `delivery_activate`（`activation_method=restart`）后，**先回执「开始生效」，再调 `gracefulShutdown`**」的顺序描述**——改为「关服原语**成功下发之后**才回执」。ADR-0070 的决策 1（平台原语 + 默认空实现）、决策 3（activated 判定归控制面心跳回归）、决策 4（含 `.jar` 必须 `restart` / 强依赖宿主自启的边界重申）**全部继续有效、不变**。

## 背景

ADR-0070 决策 2 按「先回执、后关服」编排 restart 生效，理由是「关服后进程没了就发不出回执」。落地后发现该顺序与**控制面的回执接收语义**叠加会产出无法告警的假成功：

- 控制面按命令前态 CAS 接收阶段回执（`fetched → done / failed`），**同一条命令只认第一条回执**（`DeliveryBlobService.ReceiveResult` → `cmdRepo.UpdateStatus`）。于是「先回执 success『开始生效』、关服原语抛异常时再回执 failed」的第二次回执必被拒（只落在 agent 侧的 warn 日志里）。
- 失败信号丢失的后果被放大：进程**没有**关掉 → 心跳与指标批继续上报 → 控制面 `reconcileActivatingRestart` 据「起始之后有新鲜心跳批」判 `activated`。即「关服失败」被静默改写成「生效成功」。
- 同时 `gracefulShutdown` 在 `PlatformAdapter` 上是**默认空实现且不抛异常**：未覆写该原语的平台（测试桩、只读壳、后续新平台）走到「回执 success 但进程不关」，同样落进上述假成功。

## 决策

1. **关服能力探测 fail-closed**：`PlatformAdapter` 增能力位 `gracefulShutdownSupported`（core 默认 `false`；Bukkit / Bungee 壳显式覆写 `true`）。探测不通过时**绝不回执 success**——回执 `failed` 并给出可读处置建议（宿主机手工重启 / 改选 `hot_reload` / `push_only`），控制面据此按「关服指令回执失败」判 failed 并熔断止血。
2. **单次回执收敛**：restart（正推与回滚）在**关服原语成功下发之后**才回执 success（回执语义仍是「已开始生效」，非「生效完成」）；原语抛异常时只回执 `failed`。**禁止**同一命令出现「先 success、后 failed」的双回执。
3. **回执仍须在进程真正退出前发出**：延迟触发关服（让命令执行调用栈先解开）+「原语返回即已下发、平台随后的停机序列才终止进程」共同提供送达窗口；极端情况下回执丢失也不产生假成功——生效判定真源仍是控制面心跳回归 / 超时（ADR-0070 决策 3），回执只承担加速收敛与留痕。
4. **回执不承诺 agent 无法核实的事**：阶段失败原因里的处置建议按 phase 分野——正推（`activate`）**不得承诺「可整单回滚」**（是否下发回滚由控制面按推送留痕 + 备份存在性预检决定），只给 agent 可保证的处置（手工重载 / 按同版本重推）；回滚（`rollback`）阶段备份确实已在盘，保留回滚建议。

## 理由

- **真源归属**：生效判定的真源在控制面心跳（决策 3 不变），agent 只能报「我做了什么」。把「已开始生效」回执建立在「关服原语确实被成功下发」之上，「失败」与「成功」才在控制面可区分。
- **与控制面接收口径对齐**：一条命令一条回执是控制面的既有契约（先到先得）；agent 侧不收敛的话，第二次回执只是日志噪声，还制造「失败已上报」的错觉。
- **fail-closed 优于乐观默认**：默认「支持关服」把平台能力缺失变成静默假成功；默认「不支持」的代价只是明确失败 + 可读原因，且能被运维立刻发现。

## 后果

- `PlatformAdapter` 增一个能力位（core 默认 false、双壳覆写 true）；未升级的旧壳 jar 走「不支持」分支**明确失败**，不再假成功。
- 关服原语调用本身失败时，控制面只能靠超时安全阀兜底（不再有第二条 failed 回执可挂）——这是接受单回执纪律的代价，仍是 fail-closed。
- restart 生效的真机验收前置不变（宿主自启脚本，ADR-0070 决策 4）；真机需验「能力探测拒绝 / 单次回执 / 关服失败原因可见」三条。
- 生效语义真源仍归 spec（[v2-delivery-orchestration](../specs/v2-delivery-orchestration.md) §4.6.1 / §4.6.4），本 ADR 只锁定「为什么这样编排」。

## 备选方案

- **保持「先回执 success、再关服」并允许关服失败时补发 failed**：第二条回执必被前态 CAS 拒收，关服失败被静默改写成 `activated`（正是本 ADR 要修的假成功）。否决。
- **把关服原语改成返回失败原因（`gracefulShutdown(reason): String?`）**：能表达失败，但仍发生在「先回执」之后，回执顺序问题不解决；且要改 ADR-0070 决策 1 的原语契约，改动面更大。否决。
- **agent 干脆不回执、全交给控制面心跳超时判定**：restart 的 activate 命令会长期悬在 `fetched`（影响在途命令收口），运维也看不到「正在关服」的留痕。否决。
- **回执文案保留「可整单回滚还原」不按 phase 分野**：agent 无从核实控制面预检（推送留痕 / 备份存在性），正推阶段承诺回滚等于给运维一条走不通的处置路径。否决。

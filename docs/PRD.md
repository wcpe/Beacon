# Beacon 第二版产品需求文档（PRD）

> 活文档（入库于 `docs/`，随需求变更同 PR 更新）。本文只管 **WHAT / WHY**：产品目标、需求边界、功能需求与验收。HOW 见 `docs/ARCHITECTURE.md`，前端交互见 `docs/UX.md`，版本路线见 `docs/ROADMAP.md`，演进规则见 `docs/CONTRIBUTING.md`。
>
> **第二版基线**：`v0.1.0` 到 `v0.19.x` 归入 Legacy 第一版探索期，历史保留但不再作为后续验收基准。第二版从 `0.20.x` 的 P0 规格冻结阶段开始。

## 1. 背景与目标

### 1.1 背景

Beacon 的第一版围绕配置中心、文件树、服务发现、健康检查和管理台原型逐步扩张，功能堆叠后出现路线混乱、页面不可维护、部分 FR 与当前业务目标脱节的问题。

第二版需要重新聚焦：Beacon 是一个用于串联多个 BungeeCord 与 Bukkit / Paper 子服的**集群调度中间件控制面**。它要用 Web 管理以前只能靠配置文件硬维护的环境、BC 集群、大区、小区、子服关系，并让业务插件通过本机 agent 能力完成健康调度、跨服通信、审计告警与故障排查。

### 1.2 目标

- 建立清晰的环境 / namespace / BC 集群 / 大区 / 小区 / 子服权威模型。
- 让 BC 与 Bukkit agent 只靠 Beacon 地址与 namespace token 自连接中控；namespace 由 token 推导，serverId 在待确认流程中分配。
- 通过 agent 首启身份文件绑定真实服务器，避免运维误改 serverId 导致区数据隔离出错。
- 让首次注册、换区、解绑、身份冲突都必须在后台可见、可审计、可人工确认。
- 让业务插件只依赖本机 `agent-api`，禁止直接 HTTP 调 Beacon。
- 基于 TPS、CPU、在线人数、连接、告警、容量和延迟生成健康值，供业务插件选择健康服务器安排玩家。
- 可视化玩家流、连接流、调度决策、跨服消息、异常链路和审计记录。
- 对连接明细和跨服消息 payload 做可追踪存储，并提供热 / 冷数据生命周期。
- 重做核心后台页面，让 1000+ 子服规模下仍能在 1920x1080、浏览器 100% 缩放下高密度可操作。

### 1.3 非目标

- 配置中心、文件同步、文件树预览不沿用 Legacy 旧原型继续堆改。Legacy 前端随 P1 工程化基建整体冻结（FR-138），三项能力 P7-P9 按第二版模型重新设计与验收。
- Beacon 不实现具体游戏玩法，例如经济、匹配、排行、传送规则、跨服看人 UI。
- 业务插件不得绕过 agent 直连 Beacon；控制面不是业务插件的运行时依赖。
- 默认禁止跨 namespace 调度、通信和 Agent 操作；跨 namespace 只能通过后台显式互通信任关系开放。
- 不用 agent 命令通道传大文件。命令通道只做控制面编排，数据面文件传输必须走专门的流式传输通道。
- 不建插件制品库 / 仓库，不做自动依赖解析与蓝绿切换；变更单载荷只来自黄金模板源与配置中心。

## 2. 角色

| 角色 | 说明 | 主要诉求 |
|---|---|---|
| 运维管理员 | 通过 Web 管理 Beacon 集群 | 看清全局健康、接入新服、分配区服、排查异常、处理告警 |
| 集群管理员 | 负责环境、BC、大区、小区和调度策略 | 保证 namespace 隔离、调度可信、扩区换区可审计 |
| 业务插件开发者 | 在 BC / Bukkit 侧开发业务插件 | 通过本机 `agent-api` 获取健康服务器、发送跨服消息、查询本地缓存事实 |
| Beacon agent | 运行在 BC / Bukkit / Paper 上的数据面组件 | 自注册、上报指标、接收控制指令、提供本机 API、控制面不可用时降级 |
| 审计与安全人员 | 查看操作、消息、payload 访问与跨域行为 | 所有高风险操作有原因、有记录、可追溯 |

## 3. 核心约束

- **namespace 是强隔离边界**：默认禁止跨 namespace 调度、消息、Agent 操作。跨 namespace 互通必须后台显式配置，并额外审计。
- **首次接入必须人工确认**：新 agent 注册后只能处于待确认状态，未确认、未分配区服前不可调度。
- **identityId 绑定稳定 serverId**：agent 首启生成唯一身份文件，namespace 由接入 token 推导，serverId 由控制面在首次确认时分配并绑定。换区必须走后台受控流程；FR-205 交付后 serverId 不允许原地修改。
- **业务插件只走本机 agent-api**：业务插件不得直接 HTTP 调 Beacon。agent 负责缓存、降级、限流与控制面隔离。
- **控制面 / 数据面分离**：Beacon 做编排、审计、调度决策和事实存储；游戏服继续承担玩家入口与业务执行。
- **连接与 payload 查询可控**：连接明细和 payload 可查，但默认不做大范围慢查询；payload 查看必须填写原因并写审计。
- **热 / 冷数据分层**：热库保存近期数据；2 个月以上默认归档到同实例独立 database / schema，配置预留独立归档 DSN。
- **页面面向 1000+ 子服**：核心列表必须支持搜索、分页、虚拟化或服务端筛选，禁止一次性渲染不可操作的大列表。

## 5. 非功能需求（NFR）

- **规模**：面向 1000+ 子服、多个 BC 集群、固定大区 + 多小区结构；所有列表默认分页 / 筛选 / 虚拟化。
- **性能**：Agent 1s 采样，Beacon 5s 批量入库；写入与归档采用批处理，禁止请求主线程执行长耗时任务。
- **时延基线（2026-10-11 端到端压测实测后确认）**：度量入口见 [OPERATIONS](OPERATIONS.md) §3.2（Prometheus 指标）与 §3.3（压测 harness）。参考负载为**并发 32 的混合负载**，门槛按端点类别分级——
  - 零 DB 内存读（`GET /admin/v1/topology`、`GET /metrics`）：p95 ≤ 5ms、p99 ≤ 10ms。
  - 轻 DB 读（`GET /admin/v1/system/status`、`GET /admin/v2/zone-tree`、`GET /admin/v2/servers`）：p95 ≤ 25ms、p99 ≤ 40ms。
  - v2 agent 数据面只读（`GET /beacon/v2/agent/schedule/candidates`、`POST /beacon/v2/agent/schedule/decide`）：p95 ≤ 30ms、p99 ≤ 50ms（与轻 DB 读同量级，同为分页 + 富化路径）。
  - v2 agent 数据面写（`POST /beacon/v2/agent/metrics/report` 等，成功码 202）：p95 ≤ 30ms、p99 ≤ 50ms。202 表示「已入有界队列、落库异步」，故该时延是**入队**耗时，不含写库。
  - 数据面写·agent 注册（`POST /beacon/v1/agent/data-plane/attach`）：p95 ≤ 200ms、p99 ≤ 400ms。这是全场最慢的端点（实测 p50 78ms / p95 157ms / p99 233ms @并发 32），根因是写事务 + 审计在 sqlite 单写者下的锁等待，**且降并发也压不下来长尾**；批量重注册场景（如整集群重启后）据此评估容量。
  - 管理面写（`PUT /admin/v2/servers/{serverId}/tags`）：p95 ≤ 60ms、p99 ≤ 150ms。
  - agent 心跳（`POST /beacon/v1/agent/heartbeat`）：p95 ≤ 50ms、p99 ≤ 80ms。
  - **错误率**：非 4xx 预期失败的失败率 ≤ 0.1%（各档实测 0.00%）。
  - **长轮询 / SSE 端点不适用上述时延门槛**：其耗时是真实挂起时长（最长 30s、流式传输更长），按 route 单列统计，不据其判接口 SLA；改用唤醒时延衡量（实测 p95 22~27ms）。
- **时延门槛的宿主机口径（必须先读，否则会误判）**：上述门槛对应**宿主机未饱和**状态。同代码同配置下，宿主机 load 15 / 40 核时并发 32 实测 9918 RPS、整体 p95 8.11ms；宿主机 load 36 / 40 核时同档仅 4303 RPS、p95 20.20ms——**相差 2.3 倍，全部来自争抢 CPU 而非系统自身退化**。因此做性能对比与告警判定时，必须固定或至少记录宿主机负载口径；单纯看某个时延数字越过门槛**不等于**系统退化。
- **吞吐已知约束（实测，非系统容量上限）**：修复心跳冗余 DB 查询后，并发 32、宿主机负载 6~16 / 40 核时实测约 9918 RPS；修复前同档为 6602 RPS（当时宿主机负载 26~38 / 40 核）。**两组数据的宿主机负载不同，只可作量级参考，不应据其规划容量上限。** 成因已定位为**控制面进程 CPU 而非磁盘 I/O**——同机实测控制面自身占用约 5.9 核、I/O 等待仅 1.1%，DB 连接池的累计等待是 Go 层调度等待而非磁盘等待。
  - **已修**：心跳每请求原先取 6 次 DB 连接（3 次 `HasTable` 实查 `sqlite_master` + 1 次命名空间按主键重复读，约占全库连接压力的三分之一），现降为 2 次；并发 32 下心跳 p95 19.60 → 9.45ms（同期未改动端点仅漂移 +7~22%，可作内部对照组）。
  - **待优化**：① `GET /admin/v2/servers` 每请求取 7 次连接（五次批量 `IN` + Count + Find），是当前单请求 DB 成本最高的**读**端点；② `POST /beacon/v1/agent/data-plane/attach` 是全场最慢端点（并发 32 下 p50 78ms / p95 157ms / p99 233ms，且并发降到 8 时 p99 仍达 237ms），长尾源于写事务 + 审计在 sqlite 单写者下的锁等待，**降并发也压不掉**——批量重注册场景（整集群重启后）须据此评估容量；③ `database.max-open-conns` 默认 4，是 2026-10-10 生产 P0 死锁事故后的纵深防御取值（非根治项），实测抬到 16 可使累计排队等待时间减半；④ `busy_timeout` 与 `call-timeout-ms` 同为 5000ms，取等待超时仍会把 sqlite 文件锁竞争误报成池耗尽。
  - **已优化（2026-10-12）**：`GET /admin/v1/topology` 与 `GET /admin/v1/system/status` 此前为取一个计数 / 结果集就把整个注册表**深拷贝**（每实例一次 `Metadata` map + `Backends` 切片分配，深拷贝发生在读锁临界区内、临界区随实例数线性变长）。现 topology 改用新增的 `Registry.ForEachTopology` 窄投影（只带它真正消费的 6 个标量 + 拷贝后的 `Backends`，**不碰 Metadata**），system/status 改用既有的零拷贝 `StatusCounts()`。实测（1000 台，含 Metadata 与 Backends）：topology 单次组装 **2.18ms → 1.26ms、分配 981KB → 652KB、allocs 3280 → 279**；system/status 在线数 76µs → 55µs。
    - **topology 的成本仍随实例数线性增长**（这是端点语义决定的：它必须返回全量节点与边）。1 万台外推约 12.6ms / ~1.4MB，**仍无分页、无实例数上限、无缓存**——管理台若高频轮询该端点将线性放大，需要时再补分页或缓存。本次只消除了深拷贝这一层无谓开销，未改变「全量返回」的契约。
- **规模容量（2026-10-12 实测，1000 台规模）**：把虚拟 agent 注册改造为有界并发后实测 1000 台（此前只测 64 台）。**结论：次线性，无系统性拐点。**
  - **规模不敏感的部分**：心跳与 v2 上报在 **15.6 倍规模下保持率 95.4% / 95.1%**——内存注册表（map 查找 + RWMutex）完全扛得住 1000 台。规模带来的下降集中在混入 `topology` 的负载族（57%~74%），而该端点的线性成本已见上条。
  - **判据**：高档位（并发 128）保持率**高于**中间档（并发 32）（73.8% > 65.1%）——真正的资源拐点会表现为高档位崩塌更厉害，此处相反，故判定为次线性而非拐点。
  - **容量工作点**：1000 台规模下心跳 **8,688 RPS**（p95 7.86ms / p99 11.19ms）、v2 上报 3,609 RPS、混合只读 3,622 RPS，**全部档位错误数 0**。按心跳 10s/台折算，8.7k RPS ≈ **8.7 万台子服的稳态心跳**——1000 台只用掉 **1.2%**。
  - **适用边界（必须连同结论一起读）**：① 单机 sqlite + `max-open-conns` 默认 4（换 MySQL 结论会变）；② 本宿主机 40 核，且 load1 在 7~29 间漂移；③ 上表为**单类负载隔离测量**，混合负载下**不能把各单类容量相加**（v1 核心族 6 端点加权轮转混跑仅 4,596~5,049 RPS）；④ 本机 loopback，不含真实网络 RTT。
  - **抬高连接池上限不是吞吐的解法（A/B 实测）**：同二进制、同规模、**两组控制面同时常驻交替 3 轮**（消除本机 load 漂移的时序混淆），只改 `max-open-conns` 4 → 32：心跳 RPS 比值仅 **1.05x**。且池 32 时仍有 26.7 万次池等待——说明请求在等别的东西，**池排队只是现象不是根因**；同期控制面峰值 CPU 仅 12.8/40 核、压测端 0.17~1.46 核，**两端均未饱和**。
- **背压与限流（2026-10-12 实测）**：控制面共 4 处返回 429，四类**全部可达**，三类已在真实链路上触发并验证恢复（详见 [OPERATIONS](OPERATIONS.md) §3.3）。
  - **入队计数单位是「批」不是「行」**（易误判）：`AsyncDailyWriter` 的 4096 有界队列按**批**计槽位，一个请求无论带 1 条还是 500 条事件都只占 1 个槽位。故「200 请求 × 200 事件」对队列的压力是 **4.9%** 而非 977%。实测填满需 **4000+ 个请求（约 200 万条事件）**，第 4339~4554 个请求首次回 429。
  - **交付数据面并发上限**：上传 `delivery.upload-concurrency` 默认 4、下载 `delivery.download-concurrency` 默认 64（运维热设置，满即拒**不排队**）。这是最容易确定性复现的背压路径。
  - **可观测性缺口（已补）**：产品此前不暴露队列深度，429 出现前运维无法从指标上看到积压（只有「多次重试仍失败而丢弃」的计数）。**现已有** `beacon_self_write_queue_depth{route}` 与 `beacon_self_write_queue_capacity`（见 [ADR-0091](adr/0091-control-plane-self-health-metrics.md)），容量即那个有界 channel（`len(queue)`）。
- **大文件与鉴权成本（2026-10-12 实测）**：
  - **blob 下载确认为流式**：256MiB 单流下载期间控制面 RSS 增量仅 **0.5 MiB（占文件 0.2%）**。单流吞吐 337~592 MB/s（首字节均 2ms）；并发 64 路总吞吐 3,313 MB/s，**非线性**（单流 700 → 86 MB/s），饱和点约 16~32 路。Range / `Content-Range` / 越界 416 / 分片拼接逐字节一致全部正确。
  - **登录是唯一的昂贵鉴权路径**：`POST /admin/v1/auth/login` 单请求 CPU **92ms（bcrypt）→ 单核约 11 次登录/秒**，并发 1→64 时 RPS 仅 10.9→244.5（纯排队）。对比 `/admin/v2` HMAC 令牌路径贵 **850x**、v2 agent 上报（2 次 DB 查询 + sha256）贵 **78x**——**日常接口鉴权成本可忽略，登录端点须按 11 QPS/核 规划**。
  - **无登录失败锁定**：全仓无失败计数 / 账号锁定 / IP 封禁，狂打错误凭据不会触发封禁或 429 升级；错误路径成本普遍**低于**成功路径（提前失败），故鉴权风暴不是放大器（正常请求 p95 仅 +8.2ms 且风暴后即恢复）。
- **安全**：token、密码、payload 不写日志；payload 查看必须填原因；跨 namespace 行为必须有单独审计。
- **可用性**：控制面不可用时 agent 保留本地缓存与降级能力；存在最后有效大厅候选快照时不因控制面断连阻断玩家入口，未配置或无可用大厅候选时明确拒绝且不回退普通区服。
- **可审计**：注册确认、解绑、换区、调度、命令、payload 查看、跨域操作、归档清理都可追踪。
- **存储**：热库与归档库默认同 MySQL 实例不同 database / schema；配置预留独立归档 DSN，后续可迁出。
- **UI**：浏览器 100% 缩放、1920x1080 下优先保证单页高密度操作；不做大屏装饰、地图装饰或游戏化外观。
- **兼容**：1.0.0 前允许调整契约，但每个阶段必须写清迁移影响；1.0.0 后严格按 SemVer 执行。

## 7. Legacy 策略

- `v0.1.0` 到 `v0.19.x` 作为第一版探索期冻结，称为 Legacy。
- Legacy FR、旧 P1/P2/P3 分期、旧页面原型不再作为第二版验收基准。
- 需要保留的能力必须在第二版重新立 FR、重新写规格、重新验收。
- Legacy 前端（`web/`）随 P1 工程化基建整体冻结，第二版管理台另起 `apps/web`；配置中心、文件同步、文件树预览在 P7-P9 重新设计、重新立规格、重新验收。
- 历史实现、CHANGELOG、ADR、spec 保留在仓库中，用于追溯，不再驱动新路线。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| Beacon 控制面 | 独立运行的中控服务，负责注册、调度、审计、存储和后台管理 |
| agent | 运行在 BC / Bukkit / Paper 上的接入插件 |
| namespace | 强隔离边界，默认禁止跨 namespace 调度、消息和 Agent 操作 |
| env / 环境 | 面向运维展示的环境维度，可映射到 namespace 或 namespace 分组 |
| BC 集群 | 一组 BungeeCord / Waterfall / Velocity 代理节点 |
| 大区 | BC 集群下的逻辑区域 |
| 小区 | 大区下承载一批子服的调度单元 |
| 子服 | Bukkit / Paper 服务器实例 |
| identityId | agent 首启生成并持久化的唯一身份，绑定 namespace + serverId |
| serverId | 运维可读的服务器标识，必须与 identityId 绑定后才可信 |
| schedulable | 服务器可被调度，区别于 online；未确认、未分配、禁用、排空或不健康都不可调度 |
| agent-api | 业务插件调用的本机 API，负责调度候选、消息、缓存和降级 |
| 热库 | 保存近期高频查询数据的主业务库 |
| 归档库 | 保存冷数据的独立 database / schema，默认与热库同实例 |
| 变更单 | 一次交付的最小编排单元：黄金模板源文件差异与配置变更的组合，统一走影响预览、审批、灰度、生效与回滚 |
| 黄金模板源 | 被指定为载荷来源的运行中子服，插件与配置先在其上装好验证，再扫描差异生成变更单 |

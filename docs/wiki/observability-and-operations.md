# 可观测、健康与运维操作

本文说明 Beacon v2 的日常观测闭环：先看全局健康，再定位服务器、命令、审计或告警，最后采取受审计的操作。不要把面板中的历史数据当作实时控制指令；玩家链路由数据面和 Agent 本地快照保障。

## 1. 日常巡检顺序

1. 打开「Dashboard」，按 namespace 查看在线数、健康等级、可调度数、负载趋势与调度结果。
2. 打开「Servers」，筛选异常服务器，查看身份、角色、归属、心跳、健康原因、端点事实和配置时间线。
3. 在「Topology」确认 BC、LobbyCluster、Region、Zone 与后端关系；归属变化应使用受控的 placement/改派流程。
4. 有变更或异常时，依次检查「审批中心」「命令观测」「审计」「告警事件」；不要只凭单个卡片作结论。

NOC 场景可使用只读 Wallboard；它不提供下线、排空、改派或配置发布入口。

## 2. 健康与调度

每台已确认服务器会得到 `score`、健康等级、是否可调度、原因列表与因子分解。健康分用于候选排序，不代替业务插件的玩家容量或玩法规则。

- `healthy`：正常候选，按健康分优先；同分时优先容量占用较低者，再随机。
- `degraded`：应尽快检查，但通常仍可作为靠后的候选，避免高峰期突然摘除大量服务器。
- `unhealthy`、未确认、被主动下线、排空中或达到容量限制：不可调度。

需要维护一台服时，先在服务器页启用 drain，等待玩家自然离开并验证在线人数为零，再改派、重启或下线。不要直接修改数据库，也不要把 drain 当作强制踢人。

健康权重的变更应先在测试 namespace 验证，再经「设置」更新。记录变更时间、原因和预期效果；历史快照中的权重版本可用于解释当时的评分。

## 3. 调度决策与 fail-static

调度记录的 trace ID 用于回答「为什么选择或排除了某台服」。查看时重点核对目标 Zone、候选数、排除原因、选择结果、耗时和 `source`。

控制面短时不可用时，Agent 使用最近候选快照做本地决策并在恢复后补报；这会显示为本地降级来源。此时优先修复控制面连通性，不要因单次降级记录就关闭玩家入口。快照长期未更新会被标记为陈旧，仍应尽快排查。

## 4. 命令、审计与告警

### 命令观测

命令观测展示控制面到 Agent 的命令生命周期：待领取、已领取、完成、失败或过期。它只显示元数据与结果摘要，不应展示配置正文、日志正文或凭据。

- 发布、重同步、文件读取、日志请求等操作卡住时，按服务器和命令类型过滤。
- 先确认 Agent 是否在线且身份 active，再看命令年龄和结果摘要。
- 重复下发前先确认旧命令是否仍在途，避免造成并发交付或误判。

### 审计

审计记录谁在何时对哪个 namespace/对象执行了写操作及结果。对改派、排空、密钥、配置、变更单和更新等高风险动作，必须先从审计记录回溯再继续操作。导出时遵守数据分级，避免把敏感字段带出受控环境。

### 告警事件

告警事件是异常状态的历史线索。按级别、类型、namespace 和时间窗筛选，结合服务器详情、命令结果与审计判断根因。确认或关闭事件只代表已处理，不会自动修复服务器健康。

## 5. 监控接入

控制面在**独立监听端口**上暴露 Prometheus 指标（Prometheus 文本格式），由 `config.yml` 顶层配置段 `metrics-endpoint` 控制。出厂值只绑本机回环，外部与公网默认抓不到；该端点属于运维网络面，应仅在受信任网络或反向代理访问控制之内开放，**不要**直接公开到互联网。指标适合告警和趋势，不取代管理台的详细审计和诊断。

### 5.1 抓取地址（1.5.0 起变更）

> ⚠️ **升级必读**：主端口（默认 `:8848`）**不再提供** `/metrics`。升级后若继续抓旧地址，`up{job="beacon"}` 会立即归零——**控制面并没有挂，是抓取地址变了**。

- **同机抓取**：指向 `http://127.0.0.1:8849/metrics`。
- **跨机抓取**：先把 `metrics-endpoint.listen-addr` 放开到内网地址（或用环境变量 `BEACON_METRICS_ENDPOINT_LISTEN_ADDR` 覆盖，env 优先），改后重启生效。
- **容器形态**：必须额外**映射 8849 端口**。容器内回环与宿主回环不是同一个网络命名空间，只改 `listen-addr` 而不映射，宿主侧依旧抓不到。
- **为什么独立端口**：主端口默认绑所有网卡且承载管理台与 agent 数据面，抓取挂在上面等于「主端口可达即能匿名读到实例拓扑与容量画像」，无法单独收敛暴露面。
- 抓取端点**不经过主路由中间件**，因此每次 scrape **不会**再记入 `beacon_http_requests_total`（旧版那条 `route="/metrics"` 的自记 series 已消失）。算业务 QPS 时可忽略抓取流量，但**不要**把该 series 归零误读成业务流量骤降。

抓取配置片段、Bearer 鉴权（可选）与完整降级说明见 [OPERATIONS](../OPERATIONS.md) §3.2。

### 5.2 可抓取的指标分组

| 前缀 | 含义 |
|---|---|
| `beacon_instances_*` | **被管实例**：注册量、健康等级、在线/可调度状态、发布与推送计数 |
| `beacon_self_*` | **控制面自身**：连接池等待与在用、长轮询挂起数、命令队列深度、指标写入丢弃 |
| `beacon_http_*` | **接口 RED**：请求数、耗时直方图（可按路由模板算 p95 / p99）、错误计数 |
| `go_*` / `process_*` | **Go 运行时与进程**：goroutine、堆、GC、RSS、CPU（约 40 条 series） |

`beacon_self_*` 尤其值得配告警——它暴露的是**故障前兆**：连接池等待增长（2026-10-10「所有需 DB 端点挂起」事故的直接前兆）、命令队列积压（429 背压出现前唯一的信号）、指标写入丢弃（非零即代表数据**已经丢了**）。

`beacon_http_*` 的耗时直方图按**路由模板**而非原始路径聚合（避免高基数），可直接用于算接口 p95 / p99 并设延迟告警。

建议最少建立以下告警：控制面不可达、在线实例急剧下降、不可调度实例增加、交付失败/超时、健康等级持续恶化、归档任务失败，以及上面 `beacon_self_*` 的连接池等待与指标丢弃。

## 6. 操作边界

- Agent 只报告事实并执行经命令通道下发的操作；控制面不反向连接 Agent。
- 控制面不可用不应阻断已具备本地快照的玩家进服路径；但新增审批、拓扑变更和交付应等待控制面恢复。
- 数据库中的事实、历史指标和归档数据是排障依据，不是绕过管理台约束的操作入口。

## 7. 数据口径速查

上文各页面的可核对口径如下，可直接用于判断数据是否正常：

- 指标按 5 秒一批由 Agent 上报，控制面按日期分表保存并按批次幂等去重。时钟偏移过大的批次会被拒绝并计入丢弃数；断连期间的样本按 Agent 本地缓冲策略补报或丢弃，恢复后以控制面收到的批次为准。
- 健康分范围为 0–100，与等级、是否可调度、原因列表和因子明细一并给出。调度决策包含 trace ID、候选数、排除原因、选择结果与耗时，来源字段区分控制面决策与本地降级。
- 连接明细与消息元数据同样按日期分表保存。管理面查询必须给出选择性条件（如 serverId 或玩家标识）加显式时间范围，否则会被拒绝；单次跨度上限为 168 小时，前端默认填最近 24 小时。分页默认 50 条、上限 200 条。需要更长跨度时应先导出或归档，而不是放宽查询范围。
- 命令观测只返回元数据与结果摘要，支持按类型、状态和服务器过滤并分页，列表项附带命令年龄；配置正文、日志正文和凭据不会出现在这里。
- 告警事件按级别、类型、namespace 和时间窗筛选。确认或关闭只改变事件的处理状态，不会改变服务器实际健康，也不会自动修复故障。
- **实例 `online` 字段的真源是运行态注册表**（1.5.0 起）。`online` 为真表示该实例在控制面的运行时注册表中处于 `online` 或 `degraded`（心跳陈旧但未达失联阈值）。它**不再**依据身份表状态：身份 `active` 只说明「已接入过」，进程被杀后没有任何写点会把它改回去。
  - 因此若你看到**身份 active 但 `online=false`**，那是进程真的不在线，不是显示 bug。
  - 反过来，旧版本在进程停止数分钟后仍可能报 `online=true`——**历史期间的 `online=true` 不能作为「当时还活着」的证据**。运维脚本判断存活请以当前返回值与心跳时间为准。
